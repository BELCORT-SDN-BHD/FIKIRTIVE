# 文案与信息展示规则

> Canonical owner：本文件。适用于所有产品页面、Otto 对话、状态、提示与费用展示。
> Founder 批准：2026-09-05，讨论后明确「好的。处理吧」，批准将规则纳入 design system。
> 边界：批准信息展示原则，不批准改变价格、计费时点、授权范围、取消／退款语义或新增功能。本轮只交付规范和现有实现差异，不代表线上 UI 已完成整改。

## 核心原则

默认展示用户要做的事；只有影响当前决定时才展示解释、费用和限制。
每一段辅助文字必须回答：用户现在需要知道什么，知道后会改变什么决定？没有明确答案就删除或移到可访问的详情入口。不要用小字补救含糊的按钮与流程。

## 展示决策

| 信息 | 位置与触发条件 | 验收标准 |
|---|---|---|
| 操作名称 | 按钮直接说明结果，如 `Add reference` | 无需读说明也能理解下一步 |
| 常规帮助 | 首次需要时或按需展开 | 已熟悉流程的用户无需反复阅读；重要条件不只放 hover tooltip |
| 付费决定 | 收费动作前，紧邻动作显示服务端报价、交付规格与必要后果 | 扣费前可理解并按有效授权确认；同一确认区域避免重复总价段落 |
| 处理中 | 显示用户任务与可执行操作，如 `Generating your video…` | 默认不附加「等待免费」；已付费任务的异常、待确认账务仍如实提示 |
| 成功 | 作品／结果优先，费用明细按需查看 | 不让重复的计费提醒压过结果；保留可追踪回执入口 |
| 失败／余额不足／价格变化 | 发生时就地显示影响和下一步 | 不因 minimal 隐藏失败、费用不确定或再次确认需求；退款只在权威状态确认后称已退回 |
| 内部处理细节 | 默认不显示模型、工具或内部 pipeline 名称 | 表达用户目标；调试资料进入工程日志，不混入日常对话 |

## 费用边界

- UI 价格消费现有报价权威，示例不成为硬编码价格；费用、权限和确认行为继续由对应业务合同定义。
- 普通聊天若收费，第一次收费前仍须清楚披露并取得适用授权。首次介绍后是否允许持续授权、授权范围及何时重新确认，需另经 Founder 决定；本规则没有批准该模式。
- 不把必要费用藏进 tooltip、账单页或操作完成后的 toast。精简重复解释不等于省略收费前的必要披露。
- 输入框底部不默认增加永久费用段落。若当前有效收费合同确实依赖该提示，先保留并记录差异，待替代披露方式获批、实现和验证后再移除。
- 状态文案区分已报价、处理中、已结算与退款待确认。不要用「没有重复扣费」等陈述代替真实账务证据。

## 图片理解与 references

Library 管理可复用资产；Creation 可以直接上传或引用素材并理解其内容，不要求用户先去 Library。

例如用户说「让 Aiman 拿着这款产品拍视频」，主要界面显示参考缩略图与创作动作；必要时显示 `Reading your reference…`，而非要求用户理解一个后台的「图片理解」开关。

若分析是用户主动要的结果，才用明确任务语言表达，例如 `Describe this image`。若分析独立收费，必须沿用有效费用披露与授权；是否包含在创作报价内由业务 owner 确认，不能在前端静默合并、隐藏或自动执行。

## 实施与验收

1. 枚举改动表面的辅助文字，逐项标记：操作、帮助、费用决定、状态、异常或内部细节。
2. 核对真实业务合同后，在现有 canonical component 修改；可复用措辞使用现有文案 owner，不另建覆盖整站的文案框架。
3. 逐项验证首次使用、重复使用、报价变化、失败、余额不足与键盘访问。明确记录不适用的分支及原因。
4. 同时检查 Create、Canvas、Otto、Library 的受影响消费者。文档检查或文本搜索不能替代运行界面与真实收费流程验证。
5. 向 Founder 展示实际变化，再记录 UI 验收；本规范的批准不代表之后实现自动通过验收。
