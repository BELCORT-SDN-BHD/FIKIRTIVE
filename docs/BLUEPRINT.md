# FIKIRTIVE 产品蓝图

> 这是 Founder 维护的长期产品北极星。它回答“我们为谁创造什么价值、哪些产品原则必须长期成立”。它不规定 agent 编排、merge 流程、CI 拓扑或当前任务顺序。

## 1. 产品定位

FIKIRTIVE 是面向中小商家的 **all-in-one marketing powerhouse**。

我们的用户通常不懂营销、没有完整营销团队，也不应该为了使用 AI 而先学习 prompt engineering。FIKIRTIVE 给他们完整、可亲手操作的营销工具，并提供一个能够研究、计划、创作和执行这些工具的 AI 营销操盘手：**Otto**。

产品从马来西亚与东南亚商家开始，但基础按全球产品设计：多语言、多市场、多币种和可替换渠道是长期方向，本地体验是优势而不是边界。

## 2. 核心价值循环

1. 商家提供品牌、产品、目标与真实经营背景。
2. Otto 研究并提出清楚、可检查的营销方案。
3. 商家可亲手编辑，也可让 Otto 操作同一套工具与数据。
4. 花钱或产生外部影响前，商家看见具体动作、成本与后果。
5. 系统执行创作、campaign、发布、互动与跟进。
6. 结果、来源、花费和状态被记录，成为下一轮更好的输入。

价值不在“一次生成”，而在商家能持续把想法变成可追踪、可改进的营销行动。

## 3. 长期产品原则

### 一个产品，一个 Otto

- 产品只有一个主要入口和一套业务事实。
- Otto 不是第二个 app，也不是用来遮盖不完整工具的聊天壳。
- 人工界面与 Otto 使用同一动作层、同一权限和同一数据。

### 人工完整，Otto 也能操作

每个正式上线的能力都应有完整的人类操作路径。Otto 可以在获得相应权限与批准后操作相同能力，但“可操作”不等于“可绕过审批”。

### 商家的数据属于商家

- 每个 tenant 的数据严格隔离。
- 资产、生成、修改、花费与外部动作应有迹可循。
- 系统不知道的事实显示 unknown，不伪装成成功、零或正在进行。
- 商家可以理解系统用了什么输入、做了什么，以及结果为何如此。

### 钱路可信

- 付费动作 exactly-once；重复点击、重试和掉线不能重复扣费。
- 失败按产品承诺 settle 或 refund，不能留下不明余额。
- 花费前显示用户真正需要理解的成本与动作。
- 定价集中配置，维持可持续毛利；利润来自真实价值，不来自浪费用户 credits。

### Access 由能力决定

- 用户可以同时拥有多个角色，例如 Creator 与 Approver。
- 角色是 permissions 的组合；每次访问根据 capability、tenant 和 resource 判断。
- 默认拒绝没有被明确授予的能力。
- 如某个动作需要职责分离，应由该动作的业务规则表达，而不是把整个角色永久锁死。

### 真实实现胜过功能表

- 不为“看起来完整”提供没有接通、不能兑现或会误导用户的按钮。
- 新能力先建立正确数据模型、状态和失败语义，再扩大表面范围。
- 产品安全尽量由模块接口、数据库约束和行为测试保证。

### Provider 是可替换的内部实现

用户购买的是 FIKIRTIVE 的能力与结果，不是某个底层供应商。供应商名称、切换和故障处理属于内部实现；用户面对稳定、诚实的产品能力和状态。

## 4. 产品边界

| 边界 | FIKIRTIVE 的责任 |
|---|---|
| **直接拥有** | 营销研究、内容创作、campaign、排期与发布、广告、本地发现、售前互动与成交促进、CRM、口碑、复购与增长实验 |
| **读取和验证** | 订单、付款、退款、库存、履约等经营事实，用于状态、归因和回执 |
| **明确交接** | 售后工单、退换货、物流、会计、税务、正式开票与催收 |
| **永久不做** | 代持商家资金、税务工资系统、通用 coding agent、开放第三方 agent 控制 FIKIRTIVE、白标或 NSFW 产品 |

售前付款链接可以由系统协助发送，但资金进入商家自己的账户；FIKIRTIVE 不成为商家资金托管方。

## 5. 产品结构

长期产品覆盖：

- Creation：图像、视频、画布、素材与可追踪的生成流程。
- Campaign：计划、内容组合、预算与执行状态。
- Publishing & ads：渠道连接、排期、发布、广告和结果回执。
- CRM & inbox：联系人、售前对话、分派、模板和跟进。
- Growth：分析、归因、实验、口碑、推荐、复购与唤回。
- Otto：跨以上模块研究、提案和执行，但始终受相同权限、成本和外部影响规则约束。

这是一张长期地图，不代表所有模块必须同时建设。当前开发只选择能闭合真实用户价值循环的最小完整切片。

## 6. 当前战略方向

近期重点是把 Creation 做成可以向真实商家收费的完整体验：

- 唯一、正式的创作画布，而不是长期维护两套实现。
- 生成状态由服务端权威结算，关闭页面也不会丢失已付费结果。
- 图片与视频规格真实贯通，不能答应一种规格却交付另一种。
- 参考、批次、来源、状态和花费落盘，不从坐标或 UI 顺序猜事实。
- 每次花费与结果对商家诚实可见。

具体 feature、顺序与验收在开工时结合当前代码和 Founder 决定细化，不在蓝图中冻结成永久施工表。

## 7. References 与开发细化

`docs/references/`、research、design、历史 specs 和竞品资料帮助团队理解目标与可能性，但它们默认不是当前任务。

正确使用方式：

1. Blueprint 给出宏观目标和长期原则。
2. 开工时加载与当前问题直接相关的 references。
3. 将本次范围、用户行为和验收写成小而具体的任务。
4. 用代码、数据库与测试证明结果。

这样既不会丢失宏大产品想象，也不会让旧文档继续控制今天的开发。

## 8. 修改方式

Founder 可以通过普通 PR 修改本蓝图。修改应说明改变了哪个产品方向及原因，但不需要 hash、修宪表、总审查员或额外审批 harness。
