# Fikirtive cowork — skill system master plan
Date: 2026-06-13 · Status: design (research- and code-grounded) · pending build approval
> Produced by a 9-agent design workflow (foundation → per-skill deep design → synthesis), grounded in the actual cowork/model/db code + the per-(model×mode) prompt research.

## Vision — the moat

The moat is a three-layer compounding asset, and the order matters: (1) the model-neutral @mention REFERENCE LAYER already in the repo — entities/refs that condition any generator — is the data substrate; (2) the per-(family x mode) MODEL KNOWLEDGE in a DB+admin-panel (ModelDirective) is the proprietary, founder-tuned understanding of HOW each of the 8 video models + Seedream actually behave (Kling destabilizes past ~2 motions, LTX face-merges multiple characters, i2v must describe motion-not-scene, Seedream wants natural language not tag-soup); (3) the COWORK SKILLS are the surface that turns (1)+(2) into felt value — Enhance/Coach/Guardian/ShotDoctor/Fill/Recipe each read the same knowledge base and the same entity layer, so every skill makes the knowledge investment pay off again. The flywheel: the founder edits one ModelDirective cell, no redeploy, and Enhance rewrites smarter AND Coach teaches sharper AND Guardian gates harder — one edit, N skills better. That is the moat: not any single skill (each is individually cloneable), but the accumulating, live-editable, model-specific knowledge base that ALL skills consume, keyed on a reference layer competitors do not have. The 'own-model-later' endgame is the same port: because PROVIDER is model-neutral transport (one chat() method), swapping OpenRouter->Claude for a self-hosted fine-tune trained ON the accumulated ModelDirective corpus + Fikirtive's own generation outcomes is a third transport class with ZERO skill edits — the knowledge base becomes the training set, and the skills become the distribution. The honest caveat: the moat is only as good as the knowledge is accurate and current, so the admin panel's editing ergonomics and a discipline of capturing tested directives (confidence flags) are themselves load-bearing moat infrastructure, not nice-to-haves.

## Foundation architecture

### Summary

Today cowork is two-axis-collapsed: `cowork-provider.ts` bundles three things into each provider class — the transport (a `fetch` to fal/OpenRouter), the skill's knowledge (the hard-coded system prompt), and the output parser. `CoworkProvider` in `packages/core/src/cowork.ts` has one method per skill (`planStoryboard`, `enhancePrompt`), so adding skill #3 means editing the interface AND both the Mock and Fal classes. That is the tangle.

The foundation separates THREE concerns:
1. SKILL = a capability. It owns its IO zod contract, its prompt/knowledge assembly, and a runner that turns input → chat messages → validated output. Lives in `apps/web/lib/cowork/skills/<name>/`.
2. PROVIDER = a model-neutral transport. One method: `chat(messages, opts) → {text}`. mock ($0 deterministic) / fal (OpenRouter→Claude) / self-hosted-later. Knows nothing about storyboards or prompts.
3. KNOWLEDGE = the per-(model-family × mode) enhanceDirective, in a DB table with an admin panel, read at runtime by skills that need it (enhancePrompt today). NOT in TS, NOT in repo markdown — the founder's explicit choice.

A skill run becomes: `runner.buildMessages(input, knowledge) → provider.chat(messages) → runner.parse(text) → zod-validated output`. The server action stays the thin money-safety + DB-write boundary it already is. Mock-default and "validate-before-spend / failure-never-charges" are preserved exactly as the generation provider does them. Contracts and the knowledge-read helper live in `@fikirtive/core` (already a dep, Railway-safe); everything else stays in `apps/web/lib/cowork/` (no new workspace package, per the Railway Dockerfile constraint).

One taxonomy decision threads through everything: the model IDs are version-specific (`veo3.1-fast`, `kling-2.6`, `kling-3`) but the research is per-FAMILY (Veo/Kling/Seedance/LTX/Seedream). The knowledge base keys on `family` + `mode`, with a deterministic `modelFamily(modelId)` resolver in core — otherwise the founder maintains 8 near-duplicate video directives. Mode (t2i/i2i/t2v/i2v/i2v-tail) is derived from the gen-request shape, not stored separately.

### Skill abstraction (file layout + the Skill<I,O> contract)

A cowork SKILL is a self-contained directory under `apps/web/lib/cowork/skills/<name>/` with three files, mirroring how a generation model is "one entry here + one entry there":

`apps/web/lib/cowork/`
- `provider.ts`            — model-neutral transport port (see split section): `CoworkTransport` + `MockTransport` + `FalTransport` + `createTransport()`
- `knowledge.ts`          — `getEnhanceDirective(family, mode)` DB read + in-memory TTL cache (see knowledge section)
- `skill.ts`              — the `Skill<I,O>` type + `runSkill()` helper (assemble→chat→parse, the shared spine)
- `registry.ts`          — `COWORK_SKILLS` map + `getSkill(id)` (see registry section)
- `skills/`
  - `draftStoryboard/`
    - `runner.ts`         — `buildMessages(input) → ChatMessage[]`, `parse(text) → CoworkPlan` (uses `coworkPlan.parse` + `extractJson`)
    - `prompt.ts`         — the system-prompt template (static knowledge this skill owns; the storyboard skill has NO per-model knowledge, so no DB read)
  - `enhancePrompt/`
    - `runner.ts`         — `buildMessages(input, directive) → ChatMessage[]`, `parse(text) → string` (clamp to MAX_ENHANCE_TEXT)
    - `prompt.ts`         — the base system prompt + the slot where the DB `enhanceDirective` for (family,mode) is injected

Contracts in core, `packages/core/src/cowork.ts` (extended, not replaced):
- existing `coworkRequest` / `enhanceRequest` / `coworkPlan` stay.
- add the SKILL shape the IO contract binds to:
```ts
export interface Skill<I, O> {
  readonly id: string;                       // "draftStoryboard" | "enhancePrompt"
  readonly input: z.ZodType<I>;              // request contract
  readonly output: z.ZodType<O> | null;      // null = free string (enhance)
  readonly cost: "free" | "paid";            // drives money-safety + audit
  buildMessages(input: I, ctx: SkillCtx): ChatMessage[];
  parse(text: string, input: I): O;          // throws on bad LLM output
}
export type ChatMessage = { role: "system" | "user"; content: string };
export interface SkillCtx { directive?: string; }   // knowledge injected by the runner
```
The IO CONTRACT a skill owns = its `input`/`output` zod schemas (already exist as `coworkRequest`/`enhanceRequest`/`coworkPlan`). The KNOWLEDGE it owns = its `prompt.ts` static template + (for enhance) the DB directive injected via `SkillCtx`. The RUNNER = `buildMessages`+`parse`. `runSkill(skill, input, transport, ctx)` is the generic spine: `transport.chat(skill.buildMessages(input, ctx)) → skill.parse(text, input)`. Adding a skill = one new `skills/<name>/` dir + one `registry.ts` line; the transport and actions are untouched. enhancePrompt's `enhanceRequest` must gain `model` + `mode` fields (currently the GenSpace call site at `apps/web/components/studio/GenSpace.tsx:142` sends only `{projectId, text}`) so the runner can look up the right directive — that is the one contract change the knowledge base forces.

### Skill / Provider / Knowledge split (the de-tangle)

CURRENT (tangled): `apps/web/lib/cowork-provider.ts` has `CoworkProvider` with `planStoryboard()` and `enhancePrompt()`. Each method inside Mock and Fal hard-codes its own system prompt AND its own `fetch` to `https://fal.run/openrouter/router/openai/v1/chat/completions` AND its own JSON/string parsing. Transport + knowledge + parsing are fused, and the interface grows a method per skill.

REFACTORED (model-neutral transport): the port keeps ONLY the transport.
```ts
// packages/core/src/cowork.ts — the new port
export interface CoworkTransport {
  readonly name: string;                                   // "mock" | "fal:claude-sonnet-4.5"
  chat(messages: ChatMessage[], opts?: { maxOutTokens?: number }): Promise<{ text: string }>;
}
```
`apps/web/lib/cowork/provider.ts`:
- `MockTransport.chat()` — deterministic, offline, $0. It does NOT know about storyboards anymore; it returns a tiny canned reply keyed off the last user message so the skill's `parse` still succeeds (e.g. echoes a minimal valid-JSON storyboard when it sees the storyboard system prompt, or appends cinematic qualifiers when it sees the enhance prompt). The skill-specific mock logic that was in `MockCoworkProvider` moves into each skill's `runner.ts` as a `mockReply(input)` fallback the MockTransport calls — keeping the mock $0 contract while the transport stays skill-agnostic. (Pragmatic alternative below in open decisions.)
- `FalTransport.chat()` — the single `fetch` to the OpenRouter endpoint, lifted verbatim from the two duplicated method bodies (same `Authorization: Key`, same `model: anthropic/claude-sonnet-4.5`, same `res.ok` error handling). One place, one transport. Model id becomes a constructor/env arg so self-hosted is a third class with no skill edits.
- `createTransport()` — mirrors `createGenerationProvider()`: returns `FalTransport` only when `FAL_KEY` is set, else `MockTransport`. Mock-default = $0 dev by construction.

WHAT MOVES WHERE:
- system prompts (lines 48-52, 72-75 of cowork-provider.ts) → `skills/*/prompt.ts`.
- `extractJson` + `coworkPlan.parse` (lines 35-40, 69) → `skills/draftStoryboard/runner.ts:parse`.
- the enhance clamp (line 94) → `skills/enhancePrompt/runner.ts:parse`.
- the two `fetch` blocks (53-68, 76-92) collapse into ONE `FalTransport.chat`.

The two server actions in `cowork-actions.ts` change minimally: `const provider = createCoworkProvider()` becomes `const transport = createTransport()`; `provider.planStoryboard(idea)` becomes `runSkill(getSkill("draftStoryboard"), {projectId, idea}, transport)`; `provider.enhancePrompt(text)` becomes `runSkill(getSkill("enhancePrompt"), {projectId, text, model, mode}, transport, {directive: await getEnhanceDirective(...)})`. The `via: provider.name` audit field becomes `transport.name`. All the money-safety scaffolding in those actions (owner guard, transaction, P2002 retry, best-effort audit) is untouched — it lives in the action, not the provider, which is exactly where it should be.

### Model knowledge base (DB table + admin panel — founder's choice)

The founder's decision: model-prompt knowledge lives in the DB with an in-app admin panel, editable live, no redeploy. Design:

PRISMA MODEL (`packages/db/prisma/schema.prisma`, new model + migration under `packages/db/prisma/migrations/`):
```prisma
// Per-(model family × generation mode) prompt directive injected by the
// enhancePrompt skill. Founder-editable in-app; takes effect immediately.
model ModelDirective {
  id          String   @id
  ownerId     String   @default("founder")   // single-tenant today, A3-ready
  family      String                          // "seedream" | "kling" | "veo" | "seedance" | "ltx"
  mode        String                          // "t2i" | "i2i" | "t2v" | "i2v" | "i2v-tail"
  directive   String                          // the injectable snippet from the research
  notes       String   @default("")           // founder's rationale / source
  confidence  String   @default("medium")     // "high" | "medium" | "low" | "untested"
  enabled     Boolean  @default(true)          // off → skill falls back to family-neutral base prompt
  source      String   @default("research")    // "research" | "founder" | "vision-v2"
  updatedAt   DateTime @updatedAt
  createdAt   DateTime @default(now())

  @@unique([ownerId, family, mode])            // the lookup key; one directive per cell
  @@index([ownerId, family])
}
```
Keying on `family` not raw `model` is deliberate: 8 video models collapse to 3 families (kling/veo/seedance) + ltx + seedream image, matching the research's per-family granularity and sparing the founder 8 near-duplicate edits. A `modelFamily(modelId)` resolver in `packages/core/src/gen.ts` (e.g. `veo3.1-fast → "veo"`, `kling-2.6 → "kling"`) maps the request's model to its family.

HOW SKILLS READ IT (`apps/web/lib/cowork/knowledge.ts`):
```ts
export async function getEnhanceDirective(family: string, mode: string): Promise<string | undefined> {
  const row = await prisma.modelDirective.findUnique({
    where: { ownerId_family_mode: { ownerId: FOUNDER_OWNER_ID, family, mode } },
  });
  return row?.enabled ? row.directive : undefined;   // undefined → skill uses its family-neutral base
}
```
The enhancePrompt server action resolves `family = modelFamily(input.model)` and `mode` from the request shape, reads the directive, and passes it in `SkillCtx.directive`; the runner injects it into the system prompt slot. A small in-process TTL cache (e.g. 30-60s) keeps the hot path off the DB without losing "live edit" feel; the admin save can also bust it. The i2v research rule ("describe MOTION/camera/change, not the scene") is just the `directive` text for the (family, i2v) rows — no code special-casing.

ADMIN PANEL (`apps/web/app/admin/directives/`): a server-component page listing the family×mode grid, each cell an editable `directive` textarea + `confidence`/`enabled` controls, saved by a `"use server"` action `saveModelDirective(raw)` that owner-guards (`FOUNDER_OWNER_ID`), zod-validates, upserts the row, busts the cache, and writes an `ActionEvent{type:"directive.edit"}`. Edit → save → next enhance uses it. Gate the route by the existing auth (login already exists at `apps/web/app/login`); single-tenant so any authed session = founder.

SEEDING (`packages/db/prisma/seed` or a one-off `apps/web/lib/cowork/seed-directives.ts`): an `upsert` per research cell — the per-(family×mode) enhanceDirective snippets the study produced, with `source:"research"` and the study's confidence. Idempotent upsert on the unique key so re-running is safe and never clobbers a founder edit if guarded by `source` (open decision below). The "vision-grounded enhancement" is explicitly v2: no schema change needed — it becomes a new `source:"vision-v2"` directive or a skill flag later.

### Skill registry

REGISTRY (`apps/web/lib/cowork/registry.ts`): a static, typed map — the single source of truth for "what skills exist", mirroring how `GEN_VIDEO_MODEL_INFO` is the registry for models.
```ts
import { draftStoryboard } from "./skills/draftStoryboard/runner";
import { enhancePrompt } from "./skills/enhancePrompt/runner";
export const COWORK_SKILLS = { draftStoryboard, enhancePrompt } as const;
export type CoworkSkillId = keyof typeof COWORK_SKILLS;
export function getSkill<K extends CoworkSkillId>(id: K): (typeof COWORK_SKILLS)[K] {
  return COWORK_SKILLS[id];
}
```
Each skill module default-exports a `Skill<I,O>` object (id/input/output/cost/buildMessages/parse). Registration = add the import + one map entry. No dynamic discovery, no plugin loader — that would be speculative for two-going-on-a-handful of skills; a static map is type-safe and tree-shakeable.

INVOCATION: skills are NOT called from the client. Each skill is wrapped by exactly one `"use server"` action in `cowork-actions.ts` (the trust + money-safety + DB-write boundary). The action: zod-parses with `skill.input`, owner-guards the project, calls `runSkill(skill, input, transport, ctx)`, then does the skill-specific DB write (storyboard → createMany in a transaction; enhance → pure return + audit). `runSkill` is the generic spine; the action holds the side effects. This keeps "cowork does only what a user could do, and the user could undo it."

UI SURFACING: keep the current pattern — skills surface as affordances, not a generic skill list. enhancePrompt is the ✨ Enhance chip already wired at `GenSpace.tsx:399`/`:142`; draftStoryboard is the cowork-draft entry point. The registry's metadata (id, label, cost) lets a future cowork panel render available skills, but v1 needs no generic launcher. The `cost:"paid"` flag lets the UI show a spend hint / require user-initiation for paid skills, consistent with money-safety.

### Money-safety pattern (cowork-wide)

The shared money-safety pattern is LIFTED FROM the generation provider (the proven one) and applied uniformly to every cowork skill:

WHICH SKILLS SPEND: `Skill.cost` declares it. `draftStoryboard` + `enhancePrompt` are `"paid"` (one LLM call each). Future read-only/transform skills can be `"free"`. The action branches audit + spend-guarding on this flag.

MOCK-DEFAULT ($0 dev): `createTransport()` returns `MockTransport` unless `FAL_KEY` is set — identical to `createGenerationProvider()` defaulting to mock unless `GENERATION_PROVIDER=fal`. A misconfigured prod can't silently burn money; dev/tests never touch the network. This is the single most important guard and it is structural, not a runtime check.

VALIDATE-BEFORE-SPEND: the action zod-parses `skill.input` and owner-guards the project (`findFirst({ where: { id: projectId, ...OWNED }})`) BEFORE `runSkill` ever calls the transport — exactly as `coworkDraftStoryboard`/`enhancePrompt` do today. An invalid request or non-owned project fails with `{error}` and zero spend.

FAILURE-NEVER-CHARGES: the cowork LLM call is a single synchronous chat (no download-after-charge step like fal image gen), so the charged/uncharged distinction is simpler than generation's `chargedError` — but the same principle holds: a transport `chat()` that throws (non-ok HTTP, empty output) propagates as `{error}` and the action does NOTHING irreversible. The DB write (storyboard shots) happens AFTER a successful, validated LLM result, inside ONE `prisma.$transaction` so partial state is impossible. enhance is a pure transform with no write at all.

EXACTLY-ONCE: draftStoryboard already retries on `P2002` over `@@unique([projectId, number])` and never double-creates. cowork LLM calls are user-initiated (button press), not retried by a queue, so the generation `idempotencyKey`/`GenJob.spent` ledger is not needed at the foundation; if a future cowork skill enqueues a worker job, it inherits the existing `GenJob` money-truth columns rather than inventing a new mechanism.

AUDIT: every paid skill run writes an `ActionEvent{ type: "cowork.<skill>", payload: { via: transport.name, ... } }` — best-effort (try/catch) so a log hiccup never loses a paid result, exactly as the current enhance action does. This is the hook for the future cost/credit ledger. The admin directive edits also audit (`type:"directive.edit"`).

**Sequencing rationale:** The order is dependency-forced, not preference. Phase 0 is non-negotiable first: every other skill imports Skill/runSkill/registry, modelFamily/deriveMode, and getEnhanceDirective — and the foundation explicitly requires migrating the two EXISTING skills onto the new spine, which is the safest possible first move because it has a known-good oracle (today's behavior) to regression against. Phase 1 (enhancePrompt v2) comes next because it is the minimum that proves the DB knowledge base earns its keep, and it forces the one contract change (enhanceRequest gains model+mode) that THREE later skills reuse (Coach, Fill's per-shot enhance, Recipe v2) — landing it early means that contract churn happens once. Phases 2-3 are the cheap, mostly-$0, high-trust skills and they deliberately precede the expensive batch: Guardian is a money-safety FEATURE that tightens startGen's pre-spend gate, so shipping it BEFORE fillStoryboard means the batch's 40 dispatches each inherit the guardian for free — building Fill first would mean batch-generating broken-ref shots at scale, the exact failure Guardian prevents. Coach shares Enhance's mode-derivation + ModelDirective read, so it is cheap right after Phase 1. shotDoctor and recipeMemory (Phase 3) are sticky but still 'planning is free' — no new spend mechanism — and recipeMemory carries a worker blocker (params persistence) best fixed before Fill so batch-captured recipes are recoverable. fillStoryboard is last on purpose: it is an ORCHESTRATOR that composes enhancePrompt (Phase 1), the guardian gate (Phase 2), startGen's idempotencyKey ledger, and the cost-preview pricing — it can only be built well once all its parts are mature, and it is the single largest burn, so it should ship into a codebase where every per-shot safety guard already exists and is proven.
