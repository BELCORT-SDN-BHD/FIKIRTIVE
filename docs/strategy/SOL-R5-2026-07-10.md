# Q1 独立第一性答案

## 1.1 先钉死证据状态

当前 cwd 实际不在 `main`：检出分支是 `claude/northstar-immersive`，HEAD `763a…`，而 `origin/main` 是 `9a330…`。两者的宪法文本存在差异；我以 `origin/main` 判断现行法律，以当前代码判断运行现实。这个偏差本身是一张治理险牌，不能略过。

另外，城里的页面、mock、文件和“区域存在”，不能自动换算成能力存在。当前最重要的事实是：

- 规划与设计已经非常宽。
- 可验证的外部动作、业务事件、回执、恢复路径仍很窄。
- 总规划 40 条销账表大多是“已写清”，不是“已接通并由真实商家验过”。

## 1.2 最终定位

我的定位句是：

> **FIKIRTIVE 是世界级小商家 revenue-growth OS：在获客→成交促进→复购/唤回范围内，把完整人工工作台与一个可受限授权的 Otto 放在同一动作层，并把每次外部动作结算成有来源、有结果、有恢复路径的回执。全球为底，本地为皮。**

我不用裸的“营收 OS”。那会自然承诺订单、收款、开票、应收、退款、客服和会计。`revenue-growth` 才与 B 边界一致。

SEA 是第一个约束集和训练场，不是永久身份；但“世界级”也不能只是形容词。它必须具体等于：

1. 任一市场都使用同一套核心对象和动作契约。
2. 渠道、语言、平台政策、付款习惯和节庆作为 Local Pack 注入。
3. 商家换市场、换渠道、换操作模式，不必换产品或重建记忆。
4. 人与 Otto 操作的是同一能力，不是两套真假不一的系统。

## 1.3 最终产品形态

最终形态不是“一座有很多页面的城”，而是五层共用内核。

1. **两个操作面**

   - Manual workbench：Research、Campaign、CRM、Content、Calendar、Channels、Local presence、Marketplace、Retention。
   - Otto：接 mandate、提出计划、请求权限、执行动作、报告结果。
   - 两者共享状态；人工可接管、修正、重放，Otto 不拥有隐藏后门。

2. **增长能力层**

   - 找市场与需求。
   - 定义受众、offer 和证据。
   - 创作并维护品牌资产。
   - 发布、排期、广告与渠道分发。
   - 本地发现、评价、推荐与口碑。
   - 售前对话、资格判断和成交促进。
   - CRM、生命周期、复购与唤回。
   - 量测、归因、实验和下一步建议。

3. **动作与回执内核**

   最少需要这些一等对象：

   - `Mandate`
   - `WorkUnit`
   - `Action`
   - `AuthorityGrant`
   - `ExternalEffect`
   - `BusinessEvent`
   - `Receipt`
   - `Recovery/Reconciliation`

   每个外部动作必须回答：谁授权、做了什么、在哪个平台、平台是否接受、业务是否发生、失败后如何确认或补救。

4. **商家真相层**

   包括产品、价格、毛利、库存、门店、容量、品牌声称证据、受众、会员、同意状态、订单/退款事实、历史效果和商家偏好。Otto 的长期优势来自这层，不是来自更会写 caption。

5. **政策与平台层**

   - 风险、审批、预算、租户、证据级别、频控和权限的 Policy Registry。
   - 每个平台一个明确 adapter；禁止页面宣称能力，而 adapter 实际 `not implemented`。
   - Local Pack 处理语言、平台组合、节庆、法规和市场习惯。

## 1.4 边界

边界应按“拥有哪类责任”划分，而不是按页面名称划分。

| 区域 | FIKIRTIVE 的责任 |
|---|---|
| **本体负责** | Research、内容、Campaign、发布/广告、本地发现、售前 WhatsApp、线索与 CRM、评价请求、推荐、复购/唤回、增长实验 |
| **读取并验证** | 订单、付款、退款、库存、履约、客服、发票、应收和会计事件，用于状态、归因和策略 |
| **明确交接** | 售后客服工单、退换货处理、物流、正式报价单、商家向顾客开票、催收、会计、税务 |
| **永久不做** | 代持商家资金、税务/工资系统、通用聊天、coding agent、外部 agent API、白标平台、无限使用承诺 |

有两个容易被误杀的例外：

1. **售前 conversational commerce 属于 B 档。** 产品问答、数量、个性化、交期、订金和付款链接往往就在成交路径中。
2. **FIKIRTIVE 自己向商家开具订阅/用量账单，当然属于自身经营责任。** “不做开票”只能指不替商家经营其开票系统。

## 1.5 真正护城河

按强到弱排序：

1. **跨渠道、商家侧中立性。** 平台 agent 优化平台利益；FIKIRTIVE 必须优化商家整体净贡献。
2. **回执级可靠性。** 不只是生成建议，而是知道动作是否真正发生、是否重复、是否被拒、是否带来可观察结果。
3. **商家记忆与真相。** 逐渐积累可迁移的产品、客群、毛利、容量、证据和效果知识。
4. **经结果校准的政策。** 哪类商家、什么条件、什么动作、什么授权强度更有效。
5. **跨渠道同一动作层。** 人和 Otto、内容和 CRM、线上和线下使用同一对象与证据。
6. **Local Packs。** 平台组合、语言、节庆、政策与当地购买路径。

“全图很大”“内容生成很好”“页面统一”都不是护城河。Meta 已把其 Business Agent 推进 WhatsApp、Messenger、Instagram，TikTok 也已公开 Agentic Hub 和 TikTok for Business MCP；单平台的生成、投放和优化会快速商品化。[Meta 官方公告](https://about.fb.com/news/2026/06/meta-business-agent/)，[TikTok 官方公告](https://ads.tiktok.com/business/en/blog/tiktok-agentic-hub-ai-agents-skills-mcp?redirected=1)

## 1.6 建造顺序

这是我的顺序；设计门先于点亮门，但不是所有工作严格串行。

1. **统一法律与证据基线**

   冻结一个明确 commit；消除工作树、`main`、宪法和 MASTER 的版本歧义。没有统一基线，不准宣称销账。

2. **Wave C 停在“可完整走读”的设计终点**

   收尾现有创作区，但停止继续画新大陆的精美页面。

3. **平台真相研究与假设台账**

   对每个关键动作先记录：官方能力、权限、审核、失败状态、数据保存限制、人工 fallback、验证办法和假设到期日。

4. **一次画完完整服务蓝图**

   全部大陆都必须在 job topology、IA、对象关系、人工/Otto 契约和状态机里有位置；“无白区”应解释为**没有静默遗漏**，不是假装所有未知都已解决。

5. **Otto 契约小 pass + founder 走城 UAT**

   Founder 走的是完整任务、权限、接管和结果链，不只是页面观感。

6. **同时取得 Saranghaeyo 的真实权限与基线**

   WABA、EasyStore、会员导出、品牌资产、订单/退款、Shopee、GBP 所有权必须尽早验证。不能等设计结束才发现核心数据拿不到。

7. **先建最小真相—动作—回执脊柱**

   优先接可提供订单、交易、退款、会员积分和来源事实的现有系统；不要先重建 CRM 或积分账本。EasyStore 已提供订单、顾客、交易、积分、referral 和 webhook 接口，但官方也明确 webhook 不保证送达，因此必须有 reconciliation/polling。[EasyStore API](https://postman.easystore.co/)，[Webhook limitations](https://developers.easystore.co/docs/api/webhooks/limitations)

8. **接通一条真实闭环**

   创作→审批→发布→售前 WhatsApp→成交事实→复购触发。每一环标明：

   - FIKIRTIVE native
   - 商家操作
   - FIKIRTIVE-assisted
   - 未实现

9. **过生产三闸后收费**

   租户隔离、外部副作用幂等/对账、发布与恢复、备份、告警、账单解释、能力真话表必须过闸。收费不必等全部大陆，但不能早于一条诚实可重复的闭环。

10. **在 3–5 家相似但非同一商家复现**

    Saranghaeyo 证明“能服务一个顾客”；同商家段复现才证明“这是产品”。

## 1.7 缺失大陆的建造次序

我不接受把口碑、GBP、推荐、积分一次打包成“第一梯队产品”。

1. **先做量测原语**：短链、QR、voucher token、UTM、来源确认、退款回卷。这不是一个营销大陆，而是所有大陆共同的仪表。
2. **薄做 Local presence + review request**：先人工/半自动验证 GBP 所有权、搜索词、评价请求率和实际增量。
3. **接通现有会员数据做唤回**：先利用既有积分和购买记录，不新建通用积分账本。
4. **验证 marketplace 单位经济后才接深层 connector**：每个平台是独立产品，不存在“一次接好 marketplace”。
5. **补 link-in-bio 与 email lifecycle**：email 先解决 consent、送达和顾客身份，不以“有地址”当作可营销。
6. **WA Status 只在官方能力得到证实后承诺自动化**。目前核验到的官方 Cloud API 文档覆盖消息、媒体和模板，未找到 Status 发布端点；所以它是“未证实”，不是“近零工程量”。[WhatsApp Business Platform 文档](https://www.postman.com/meta/whatsapp-business-platform/overview)
7. **AEO 保留为测量型 trial**，不建立独立神秘优化产品。

# Q2 对抗攻击

## 2.1 T1：杀掉原句，保留方向

“全球为底、SEA 为第一批”不是新升级，已经是现行宪法方向。真正新增的是“营收 OS”，而它与 T2 的永久边界直接冲突。

商家看到“营收 OS”时，合理预期会包括订单、报价、收款、开票、应收和客服。产品随后解释“这些都不做”，不是边界清晰，而是定位诱导。

**可证伪法：** 给 20 个目标商家只看定位句，让其列出预期能力；若超过 30% 自发写出开票、收款、订单或售后，原句失败。

**历史反例：** 项目已经出现过“设计范围快速扩张、执行内核未同步”的结构；[SOL-R4](/Users/winnin/Desktop/FIKIRTIVE/docs/strategy/SOL-R4-OPTIMIZE-2026-07-10.md) 记录的是约 65 条路由、六万行级新增，而回执与真实发布仍未成立。继续扩名词只会再制造语义债。

**替代：** `world-class ALL-IN-ONE marketing and revenue-growth OS`。

## 2.2 T2：边界方向对，但“永久按名词切割”是错的

“永久不拥有开票/会计/客服系统”可以成立；“永远不碰这些能力”不能成立。B 档要成交，就必然遇到：

- 数量与阶梯价。
- 定制 proof 与修改。
- 订金和付款方式。
- 交期、取货、配送。
- 成交后退款导致的归因回卷。
- 售前问题与售后工单的身份连续性。

尤其婚庆批发零售，正式报价和服务对话并不总能按“成交前/成交后”整齐切开。

**可证伪法：** 影随 50 条真实 WhatsApp 成交线程，标出每条消息所属工作。如果超过 10% 的成交必经动作落入被永久排除的“报价/客服”，T2 的名词边界即失败。

**必须改成：** 不拥有这些系统，但定义 `read → trigger → handoff → receipt` 契约；区分“商业 offer/估价”与“会计正式报价单”，区分“售前 conversational commerce”与“售后 service desk”。

现行宪法仍写有 auto reply/customer service，因此 T2 若入法，必须正式取代旧义，不能让两套法律同时存在。

## 2.3 T3：三项不能一起入法；只能作为有期限的设计 trial

“第一性功能对等”值得保留，但它仍可能沦为 WHAT-pass：把龙头所有 feature 拆成工作，再把每个工作安排一个 mock，不等于机制成立。

“全图先设计”有价值；“设计不许白区”若被执行成“所有未知必须预先回答”，会制造假确定性。

“连后台即成品”若被理解为接后台后一处设计都不改，则必败。权限拒绝、审核等待、部分成功、幂等冲突、平台回执缺失，都会改变用户看到的状态和恢复动作。GBP API 并非公开即用，访问要审核，且自动动作需要特定授权；平台甚至保留停用 API 的权利。[GBP API FAQ](https://developers.google.com/my-business/content/faq)，[GBP API policies](https://developers.google.com/my-business/content/policies)

**成本估算：** 仅 65 路由 × 6 个基本状态 × 2 类设备，已经是 780 个设计判断格；再乘 owner/creator/approver，达到 2,340 格，尚未算渠道、门店、语言和权限。Agent 能快速生成格子，不能替 founder 决定格子里的真相。

**可证伪门槛：**

- 先冻结 dated baseline。
- 接入三个最难 connector 后，核心 IA 改动不超过 5–10%。
- 每个能力都有真实成功、权限不足、平台拒绝、超时、部分成功和恢复状态。
- 若超过 20% 动作只能靠未披露人工 fallback，trial 失败。

只有通过后，才把教义升级为长期法律。把“trial”直接写成宪法，是把实验与法律混为一类。

## 2.4 T4：杀掉“口碑经济”捆绑包，也杀掉基于薄证据的升序

所谓口碑经济实际是四个风险完全不同的产品：

1. 评价归集。
2. 请评与 consent。
3. 推荐与防作弊。
4. 积分/value ledger。

把它们捆成第一梯队，会偷偷引入第二条 money path。

顾客一号的“FB 金矿”和“GBP 零存在”目前都还是搜索快照与假设，不是账户后台事实。GBP API 又有审批与授权门槛。更危险的是，Google 明确禁止用免费商品、折扣等激励换取评价；所以“请评”必须和“积分/奖励”物理、文案、事件上分开。[Google Business Profile review policy](https://support.google.com/business/answer/3474122?hl=en)，[Google Maps incentivized-content policy](https://support.google.com/contributionpolicy/answer/16597558?hl=en)

**我的成本估算：**

- 薄 GBP/请评实验：M，取得所有权后约 1–3 周。
- 跨平台评价归集与回复：L，约 1–2 月并持续维护 connector。
- 推荐、防作弊、退款回卷：L–XL。
- 通用积分账本：XL，且有持续财务与争议责任。
- 单一 marketplace 深接：L；每加一个平台再付一遍维护税。

**可证伪法：** 先拿到顾客一号后台，量出来源收入、搜索需求、评价请求转化、复购池和净贡献。若 reputation+GBP 只解释不到 20% 的可争取机会，就不能称双首建。

正确动作是：量测原语先行，GBP/评价薄试，既有会员唤回先行；积分账本和全量 referral 暂缓。

## 2.5 T5：保留决策闸，杀掉严格串行

T5 的问题不是收钱太早，而是把 discovery 排在设计/UAT 之后。

如果平台权限、商家数据、真实 WhatsApp 成交线程直到后面才拿到，前面的“全图定稿”会建立在虚空上。届时要么推翻设计，要么为了保护设计而扭曲事实。

**反例：** 一个 GBP 所有权拿不到、WABA 不可用、EasyStore 字段不完整的 Saranghaeyo，足以使多个已定稿页面失去现实动作。

**替代序列：** 四条 lane 从现在并行：

1. 城与全图设计。
2. 平台真相与权限。
3. Otto 契约。
4. R3/R4 生产安全与顾客一号基线。

闸门仍按顺序过，但研究和权限不准排队等候。

“收钱点不后移”也不能成为日期承诺。它只能是条件句：**一条签约能力单元真实成立、生产三闸通过，就可收费；未通过则不能拿宏大设计抵账。**

## 2.6 T6：直接杀死事实前提；只保留 Saranghaeyo 作为 assisted pilot

“全链城内已有区可通”是假的。存在的是设计区，不是运行闭环。

- Facebook/Instagram 的 `publish` 仍指向 [`notImpl`](/Users/winnin/Desktop/FIKIRTIVE/apps/web/lib/channels/meta-shared.ts:15)。
- 测试甚至明确要求 organic publish 在 worker/App Review 落地前 fail closed：[registry.test.ts](/Users/winnin/Desktop/FIKIRTIVE/apps/web/lib/channels/__tests__/registry.test.ts:26)。
- 当前 [schema.prisma](/Users/winnin/Desktop/FIKIRTIVE/packages/db/prisma/schema.prisma) 没有形成 Campaign、Contact、Conversation、Order、BusinessEvent、Receipt、Loyalty、Referral、Member 这一套闭环领域对象。

所以“创作→排期发布→WhatsApp 接单→成交回执→会员唤回”目前不是一条全链，只是五个相邻名词。

第二个错误是把 voucher/UTM 写成“诚实归因”后容易滑向因果。它们最多证明 source-observed 或 attributed；不能证明 incrementality。优惠本身还会改变购买行为。

**原生闭环证伪测试：**

- 新租户从零开始。
- 不准手改数据库。
- 每环都有动作、状态、权限、失败恢复和回执。
- 同一动作可由人或 Otto 发起。
- 月一只能报告 observed/attributed；没有对照组不得说增量。

Saranghaeyo 仍是好载体，但必须叫 **concierge-assisted pilot**。最优真相入口是先读 EasyStore 的订单、交易、退款、顾客、积分与 referral，再做 reconcile；不是先造自己的交易系统。

## 2.7 T7：风险名称大致对，现有对策基本不够

“质检官编制”不能解决判断带宽。它可能只是把 founder 的判断队列改名成质检队列。

“整图融合+商家记忆+回执脊柱”也还不是护城河，只是护城河假说。Meta 与 TikTok 的原生 agent 已在向创作、消息、广告和优化推进；竞争窗口不会等整座城全部点亮。

更致命的是 T7 漏了五张结构性风险：

1. FIKIRTIVE 用量收费与商家最优动作之间的利益冲突。
2. 同区域、同品类商家之间的策略冲突。
3. 外部内容对 Otto 的 prompt injection。
4. 商家自报回执污染学习。
5. 员工拒绝使用、转回私人 WhatsApp 的组织阻力。

WhatsApp 当前条款也并非“接通即可”。AI provider 的使用与 Business Solution Data 训练/改进共享模型受到限制，具体产品形态需要持续政策判定。[WhatsApp Business Solution Terms](https://www.whatsapp.com/legal/business-solution-terms)

**止损改写：** 每个 T7 风险都必须有 owner、触发阈值、暂停动作、恢复条件和最大暴露；否则不是风险管理，只是风险文学。

# Q3 Unknown unknowns

## 3.1 FIKIRTIVE 自身的“用量—建议”利益冲突

如果 Otto 多做动作就多消耗 credits，FIKIRTIVE 在经济上会偏好“做更多”，而不一定偏好“不做、用免费渠道、等待、降低频率”。

**为何文档链必漏：** 文档反复批判平台 agent 的利益冲突，却默认 FIKIRTIVE 天然代表商家；定价讨论计算毛利，没有审计建议为何产生。

**首测：** 同一证据分别在 flat subscription 与 usage pricing 下盲跑。若建议数量、付费动作占比显著变化，商家侧中立性尚不存在。

## 3.2 同区域竞争商家冲突

服务 Saranghaeyo 后再服务 JV 或邻近婚庆店，租户隔离只能防数据泄漏，不能解决经济冲突。两边可能被推向同一关键词、同一受众、同一 campaign window，互相抬高 CPC。

**为何必漏：** 当前模型把 `ownerId` 当成完整伦理边界，却没有“多委托人利益冲突”对象。

**首测：** 两个合成同品类租户并行生成 90 天计划，检测关键词、受众、offer 和档期碰撞；建立 disclosure、non-exclusivity 和 conflict register。

## 3.3 外部内容会成为敌对指令载体

评论、网页、PDF、OCR、WhatsApp 消息和竞对广告都可能包含“忽略规则、改变预算、联系这个号码”等文本。Research 的“有来源”只证明来源存在，不证明内容可以当指令。

**为何必漏：** 当前证据阶梯区分来源强弱，却没有区分 `data` 与 `instruction`，也没有 taint propagation。

**首测：** 给评论、网页和附件植入对抗指令；任何外部文本若能扩大 scope、改变 authority 或触发工具，立即判失败。

## 3.4 Merchant-confirmed 不是干净真相

商家可能误记、选择性上报、把自然成交归给 Otto，或为了继续取得优惠而确认“有效”。若这些标签进入策略学习，系统会把礼貌反馈学成因果。

**为何必漏：** 文档把 merchant-confirmed 当证据等级，但没有标签操纵、抽审和退款回卷模型。

**首测：** 将确认结果与 EasyStore 订单、支付、退款和时间窗抽样核对；未经外部事实支持的确认不得提升共享 policy。

## 3.5 B 边界可能切穿真实成交工作

婚庆与批发成交经常同时包含产品组合、数量价、proof、修改、订金、交期和配送。它们从顾客视角是一段对话，不是“营销结束后才进入运营”。

**为何必漏：** 现有边界从软件品类名词出发，没有从真实 conversation trace 出发。

**首测：** 影随 50 条 Saranghaeyo 成交线程；若超过 10% 的必经动作无法由本体或清晰 handoff 覆盖，边界要重画。

## 3.6 买单者与每天使用者不是同一个人

老板可能喜欢 Otto，员工却可能把它视为监控、额外录入或抢工作，于是继续使用私人 WhatsApp、口头订单和 Excel。

**为何必漏：** 当前文档主要以 founder/merchant owner 为单一行为主体，缺少 staff、approver、店员和兼职人员的激励模型。

**首测：** 老板与员工分开访谈；量测 shadow-channel 比例、确认完成率和每周 rescue minutes。

## 3.7 QR 与短链会进入物理攻击面

贴纸可被覆盖，海报会过期，二维码可被恶意替换，开放重定向会变成钓鱼基础设施。一旦印刷，错误无法靠部署回滚。

**为何必漏：** 现有系统主要把外部副作用理解为 API 动作，没有把 physical placement 当成有版本、有位置、有撤销成本的资产。

**首测：** 每个 QR 必须有 placement ledger、品牌中间页、目标 allowlist、异常地域/设备告警和一键吊销。

## 3.8 量测工具本身会改变业务

优惠码为了可归因而提供折扣，会提高转化、降低毛利，并把 Otto 训练成偏好“容易量测的折扣动作”。这不是单纯 attribution 问题，而是 measurement intervention。

**为何必漏：** 当前链条讨论证据等级，但没有把测量手段作为 treatment。

**首测：** 优先使用无折扣 token；同时看净贡献、AOV、复购和退款，而不是只看 code redemption。

## 3.9 季节性可能杀死订阅，而不只是污染实验

Raya、婚礼旺季和年终采购可能让产品一年只有几个月高价值。即使 campaign 有效，全年订阅仍可能不成立。

**为何必漏：** 当前计划以月一和 2–3 个月实验为中心，没有覆盖 12 个月 willingness-to-pay 曲线。

**首测：** 设计 seasonal pack、pause/resume 或 peak-based pricing；追踪淡季留存，而不是把停订都解释为产品失败。

## 3.10 积分是第二条 money path

积分会涉及发放、过期、退款扣回、负余额、重复消费、门店合并和争议。若 FIKIRTIVE 自己成为积分账本，它已跨过 T2 所声称的边界。

**为何必漏：** “口碑经济”把积分写成增长功能，避开了 value ledger 与财务责任视角。客户忠诚奖励也可能产生履约义务；具体会计处理须由会计师确认。[IFRS 15](https://www.ifrs.org/issued-standards/list-of-standards/ifrs-15-revenue-from-contracts-with-customers/)

**首测：** 首阶段只读 EasyStore 积分并触发唤回；除非证明确有跨系统缺口，否则不建自己的余额真相。

## 3.11 AEO 可能是一种伪产品类别

Google 2026 官方指引明确说 AI search 仍使用既有 SEO 基础，不需要特殊 AI 文件或所谓神秘优化；批量生成低价值页面还可能触犯 spam policy。[Google AI search guidance](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)，[Google 对生成式 AI 内容的指导](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)

**为何必漏：** 现有 AEO 论证的供应商材料比本地硬结果多，而“前瞻押注”会降低证伪意愿。

**首测：** 只卖可测量结果：被索引、品牌提及、引荐流量、合格线索；若不存在超出正常 SEO/内容工作的独立动作，就并回 SEO，不保留独立大陆。

# Q4 险牌

## 4.1 成本口径

以下是规划量级，不是供应商报价；计算的是 founder 判断带宽、平台等待、验证和长期维护，而不是纯代码行数。

- **S**：可逆；≤2 founder decision-hours，通常一周内可验证。
- **M**：一个跨区切片；约 0.5–2 founder-days，1–3 周验证期。
- **L**：一个难 connector、核心状态迁移或合规面；约 3–10 founder-days，1–3 月并持续维护。
- **XL**：钱样账本、跨平台核心本体或持续法律/信任责任；超过 10 founder-days，长期运营负担。

所有百分比阈值都是本轮建议值，拿到真实基线后校准。

## 4.3 最先挂墙的五张

1. 全图假定稿。
2. 闭环假原生。
3. 归因吹成因果。
4. 平台/API/政策锁死。
5. FIKIRTIVE 自利偏置。

最终裁定很简单：**主脑正确识别了方向，但仍在用宏大教义替代可失败的产品契约。** T6 的运行事实必须撤回；T1 改成 `revenue-growth`；T3 留在 trial；T4 拆包；T5 改为并行 discovery、顺序过闸。只有当设计主张被改写成触发阈值、失败成本和停止动作，它们才有资格成为法律。
