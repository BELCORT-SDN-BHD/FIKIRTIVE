# Worker 拆两个服务(#796 / #760)—— 运维怎么落地

> 本页描述**仓库里已经存在的能力**和落地时要做的动作,不报告任何 live 环境的现状。
> Railway 上现在有几个服务、各自的变量是什么,必须现场查;查不到写 `Unknown`。
> 把生产配置搬进仓库是 #797 的活,本页只讲这一次拆分要按什么形状做。

## 一句话

同一个 worker 镜像,靠 `WORKER_ROLE` 分成两种服务:**算力型**扛 ffmpeg,**等待型**扛供应商等待。

**不设 `WORKER_ROLE` 时的行为与 #796 之前一字不差** —— 七条队列各并发 1、两个连接池都用各自的
默认值、清道夫与发布调度照旧、心跳仍写 `worker` 那一行。抬并发是一个**要人点头的动作**,
不是升级的副作用:它要求把 `WORKER_ROLE=wait` 明确写出来。所以这次改动可以先合、后拆。

## 两个服务

| | 算力型 `WORKER_ROLE=compute` | 等待型 `WORKER_ROLE=wait` |
|---|---|---|
| 队列 | `ingest` `render` `caption` | `gen` `refgen` `research` `publish` |
| 在忙什么 | ffmpeg / ffprobe / whisper —— 吃 CPU 和内存 | 等 BytePlus / LLM / Meta 回话 —— CPU 基本闲着 |
| 进程内并发 | 恒为 1 | gen 4 / refgen 2 / research 2 / publish 2(可配) |
| 怎么扩容 | **加副本 + 调大容器** | **调进程内并发** |
| 清道夫 / 发布调度 / 夜间备份 | 不跑 | 跑 |
| 心跳行 | `worker-compute` | `worker-wait` |

镜像仍然只有 `apps/worker/Dockerfile` 一个,两个服务用同一个镜像、同一条启动命令,只差环境变量。
(不拆时,单服务写的心跳行仍是 `worker`。)

## 落地步骤(**先停后起**,不是改个变量了事)

先把一件事说清楚,因为它决定了整套顺序:**改环境变量 = 换一个进程**。平台的做法是起新进程、
把旧进程 `SIGTERM`,而旧 worker 有 **30 秒优雅关停窗**(`apps/worker/src/index.ts` 的
`boss.stop({ graceful: true, timeout: 30_000 })`)。这 30 秒里新旧两个进程**同时活着** ——
两份 supervision 在扫同一批钱路行,两份供应商闸门叠成 6+6=12,越过可用额度 8。
所以下面第 3 步必须是**硬序**:停 → 确认退出 → 再起。

1. **新建算力服务**:同 repo、同 Dockerfile,设 `WORKER_ROLE=compute`,其余变量与现有 worker 一致。
   - 此刻现有服务仍是 `all`(七条队列各 1、supervision 开)。新服务 supervision **关**,
     所以两个进程不会同时跑清道夫。
   - 两个进程会同时消费 `ingest/render/caption`,这是**允许**的:队列消费者本来就可以多副本,
     pg-boss 保证一条消息只投给一个消费者。
   - 供应商并发此刻**没有变化** —— 算力服务一条供应商队列都不碰。这一步可以直接起,无需停机。
2. 确认算力服务启动日志里有 `role=compute — consuming ingest×1, render×1, caption×1`。
3. **把原服务从 `all` 换成 `wait` —— 停 → 确认 → 起**(低峰做):
   1. **停掉原服务**(Railway:该服务副本数调 0,或直接 stop)。
   2. **确认它真的退出了**:日志出现 `[worker] SIGTERM — shutting down`,且服务实例列表里
      不再有活着的实例。**看到进程真的没了才继续**,不要靠掐表。
   3. 设 `WORKER_ROLE=wait`,再把它起回来。确认日志 `role=wait — consuming gen×4, …`。
   - 这个空窗里等待型队列暂时没人消费:**消息留在 pg-boss 里不会丢**,商家的任务停在
     QUEUED,恢复后照常被取走。空窗远小于 QUEUED 清道夫的 25 分钟窗口,而且清道夫还有
     一道 pg-boss 存活检查(消息还在就跳过),所以短暂空窗不会误退款。
   - 这是**唯一**一次供应商并发抬升,而且只发生在一个进程上。
4. 观察一轮之后,再按需要给算力服务加副本 / 调容器规格,给等待服务调并发。

**回退(同样是先停后起)**:

1. 停掉 `wait` 服务,确认实例退出;
2. 删掉它的 `WORKER_ROLE`(回到 `all`),起回来;
3. 确认日志 `role=all — consuming …×1`(七条队列各 1);
4. 再停掉算力服务。

顺序的理由和正向一样:`all` 和 `wait` 都跑 supervision、都开供应商闸门,两者**任何时刻只许有一个活着**。
不需要回滚代码。

> ⚠️ 不要反过来做(先加 `wait` 再缩原服务),也不要靠「改变量让平台滚动替换」——
> 那两种做法都会让两个 supervision 进程和两份供应商闸门共存一段时间。

### 如果平台不支持先停后起(操作垫片)

Railway 这类平台在改变量时是**先起新的、再停旧的**。如果你无法真正做到「停 → 确认 → 起」,
就用**降闸门垫片**兜住过渡期的总额度。

先把一件容易漏掉的事挑明:**改闸门这个动作本身也是一次滚动替换**。所以要验算的不是一段
数学,是**三段**,每一段都有一个新旧并存的窗口。设当前上限 `L`(默认 6)、垫片值 `S`,
可用额度 8:

| 段 | 动作 | 重叠窗口里的总闸门 | 约束 |
|---|---|---|---|
| ① | 把闸门从 `L` 降到 `S` | 旧 `L` + 新 `S` | `L + S ≤ 8` |
| ② | 改角色(两边都在 `S`) | `S` + `S` | `2S ≤ 8` |
| ③ | 把闸门从 `S` 改回 `L` | 旧 `S` + 新 `L` | `S + L ≤ 8` |

**`L = 6` 时,三段一起解出 `S ≤ 2`。** 逐段验算:

- ① 6 + 2 = **8** ≤ 8 ✅
- ② 2 + 2 = **4** ≤ 8 ✅
- ③ 2 + 6 = **8** ≤ 8 ✅

所以垫片值是 **2**,不是 3 —— r3 的文档写 3 时只验算了第 ②段(3+3=6),漏了①和③:
6 + 3 = **9 > 8**,两头都越额度。

具体操作:

1. 把原服务的 `PROVIDER_MAX_CONCURRENT_REQUESTS` 改成 **2**,等它生效(段①);
2. 再做角色切换,并给新的 `wait` 服务也设 `PROVIDER_MAX_CONCURRENT_REQUESTS=2`(段②);
3. 确认旧实例已经消失之后,把 `wait` 改回 6 或删掉取默认(段③)。

> **算不平就别走这条路。** 如果你的当前上限 `L ≥ 8`(或按上表解不出 `S ≥ 1`),
> 这条垫片路**此路不通** —— 必须回到上面的「停 → 确认 → 起」硬序。垫片是给
> 「平台不给你先停后起」的情况兜底的,不是给「懒得停机」用的。

supervision 的重叠没有垫片可打,但那 30 秒里它是**安全的**:每个清道夫写都是条件 CAS,
两个进程同时扫最多是重复扫一遍、日志分裂,不会重复退款(这一点判官已经核过)。真正必须
用垫片兜住的是供应商额度 —— 那一头超了就是 429,商家读作「生成失败」。

### 首次部署也必须先停后起(**没有豁免**)

**把这个 PR 第一次部署到现有 `all` 服务,同样要走「停 → 确认 → 起」。**

r4 的文档在这里写过一句假话,现已删掉:「旧进程根本没有闸门,所以那次部署只会变好、
不需要垫片」。**没有闸门 ≠ 没有请求** —— 恰恰相反,没闸门的那一头正是**没有上限**的那一头。
把峰值算出来就看见了。

旧进程跑的是 #796 之前的代码:`all` 形状下 gen 与 refgen 各消费 1 件,而一个图片任务会为
它的**每张图**各发一个付费请求(gen 的 count 上限 4,refgen 上限 6)。所以滚动窗口里:

| 谁 | 同时在飞的付费请求 |
|---|---|
| 旧进程(无闸门,gen 4 + refgen 6) | **10** |
| 新进程(闸门默认 6) | **6** |
| **重叠窗口峰值** | **16** |

**16 > 账户额度 10,更远超可用预算 8。** 超出的请求回来就是 429,商家读作「生成失败」。

而且**这一次垫片救不了**:垫片的做法是把两边的闸门都调低,但旧进程那一头**没有闸门可调**,
它的 10 是代码写死的。就算把新进程的闸门压到最小的 1,峰值仍是 10 + 1 = **11 > 10**。
解不出可行值 ⇒ 这条路不通 ⇒ 首次部署只能停机切换:

1. 停掉现有 `all` 服务,按上面第 3 步的办法**确认实例真的退出**;
2. 再把新版本起回来(`WORKER_ROLE` 仍然不设 = 保持 `all`)。

空窗期的安全性与上面一致:消息留在 pg-boss 里不会丢,清道夫窗口远大于这段空窗。

## 供应商额度:按**请求**算,不按任务算

这是 #796 判官轮改掉的一处假账,别再按老口径推:

- 账户额度管的是**同时发出去几个请求**(2026-08-08 `arkcli models get` 实测
  `concurrent_requests: 10` / `create_task_rpm: 600`)。
- 一个**图片任务**会为它的每张图各发一个付费请求(gen 的 count 上限 4,refgen 上限 6)。
  所以「gen 4 个任务 + refgen 2 个任务」在最坏情况下是 4×4 + 2×6 = **28 个并发请求**,
  而不是 6。任务槽位从来就不是请求上限。
- 真正的上限是进程内的**请求闸门**:`PROVIDER_MAX_CONCURRENT_REQUESTS`,默认 **6**,
  由 gen 与 refgen **共用**(同一个账户)。超出的请求排队等待,不会变成 429 —— 429 对商家
  来说就是「生成失败」。视频任务按**整个任务**占一个位(提交 + 轮询全程)。
- 副本数的乘法只有你能做:

  ```
  replicas × PROVIDER_MAX_CONCURRENT_REQUESTS ≤ 8      # 账户 10 减 2 的余量
  ```

worker 每次启动都把这行明账打进日志(`provider REQUESTS: hard cap 6 concurrent per replica … Keep replicas × 6 ≤ 8`)。

## 数据库连接:两个池都要算

一个 worker 进程开**两个**连接池,少算哪个都会低估一半:

| 角色 | Prisma(`DB_POOL_MAX`) | pg-boss 自己的池 | 每副本合计 |
|---|---|---|---|
| 不设变量(`all`) | 10(packages/db 默认) | 10(pg-boss 默认) | **20** |
| `compute` | 10 | 10 | **20** |
| `wait` | 24(未设时按并发自动定) | 14(按并发显式配) | **38** |
| web(每副本) | 10 | 2 | **12** |

预算公式:

```
Σ(每类服务的副本数 × 该类每副本合计) ≤ 数据库的 max_connections（留出运维/迁移的余量）
```

例:web ×2 + 算力 ×2 + 等待 ×1 = 2×12 + 2×20 + 1×38 = **102** 条。

`DB_POOL_MAX` **建议就让它不设**(等待型会自动取按并发算出的下限)。如果你按副本数手算过一个
更小的值,worker 会保留你的值并在启动时警告 —— 它不覆盖你的决定,因为只有你知道副本数。
启动日志里那行 `postgres connections: prisma X + pg-boss Y = Z per replica` 就是当次的真实口径。

⚠️ **`DB_POOL_MAX` 千万别设成负数。** 负数不会被兜底成默认值:连接池拿到 `max ≤ 0` 之后,
在**一条连接都还没建**的时候就判定自己已满,于是这个进程一条连接也开不出来,每条查询无限等待。
明账会把这种情况原样点出来(`prisma 0 (configured -3 …)` 加一行 `WARNING`),合计里按**真实容量 0**
计,不会再把那个负数当条数加进总和。

## 平台探针指哪个端点(重要)

| 端点 | 是什么 | 谁指它 | HTTP |
|---|---|---|---|
| `/api/health` | **存活** —— 这个进程还答不答得出话 | 外部 uptime 监控;人工诊断 | **恒 200** |
| `/api/ready` | **就绪** —— 这个容器该不该接流量 | **Railway 的 `healthcheckPath`**(部署闸);外部 uptime 监控 | 200 / 503 |

**Railway 只有一个 HTTP 探针,它是部署闸**(C1b ② 更正)。这张表原先写着「重启探针指
`/api/health`」—— Railway 没有这样一个探针:`apps/web/railway.json` 里的 `healthcheckPath`
是**部署**闸(新容器答 2xx 之前流量留在旧部署),而重启走的是 `restartPolicyType: ON_FAILURE`,
即进程退出才触发,不读任何 URL。于是那句话描述的分工从来没有被任何配置实现过,而闸门实际
指着的正是那个恒 200 的端点 —— 下面「迁移没跑成 → 旧部署继续承载」的承诺因此一直是空的:
迁移失败的新容器照样过闸、照样接管生产。`healthcheckPath` 现已改指 `/api/ready`,那句承诺
到此才第一次生效。`apps/web/lib/__tests__/railway-config.test.ts` 按「闸门端点必须答得出非
2xx」这条**性质**钉住它,不只是比对路径字符串。

**存活恒 200,而且不依赖任何下游。** 这一条是被判官纠正过的:存活端点从前会去查一次数据库,
库不可达就回 503 —— 而它正是重启探针指的地方。于是一次数据库故障会变成「重启还活着的 Web」,
每一轮重启又跑三次迁移重试,循环起来,恰好是这张票要消灭的那个东西。现在心跳读取是**顺带的**
(1 秒不回就放弃),读不到就如实写 `"db":"unknown"` / `"worker":"unknown"`,状态码一律不变。

**该不该接流量由 `/api/ready` 专管**:迁移没跑成 → 503;数据库不可达 → 503。
`apps/web` 的启动脚本在迁移跑不成时仍然把站点起起来(旧结构上的站点强过没有站点),
这两件事必须配套:少了就绪端点,滚动发布会把流量从好用的旧容器切给跑在旧结构上的新代码;
少了「照样起站点」,一次迁移故障就是整站 crash loop。

- 迁移失败时:`/api/health` → 200(body 里 `"migrations":"failed"`),`/api/ready` → 503。
- 数据库不可达时:`/api/health` → 200(`"db":"unknown"`),`/api/ready` → 503。
- 部署后人工核对:先看 `/api/ready` 是不是 200,再看 `/api/health` 的 `migrations` 字段。
- 把这两个信号接进告警属于 #793;在那之前是人工核对。
- ⚠️ 别再拿 `/api/health` 的 HTTP 码判断系统健康 —— 它现在只回答「Web 进程活着」。
  要判断整体,读 body 的 `db` / `worker` / `migrations`,或直接问 `/api/ready`。

## 已知边界(本票不做)

- **同租户公平**:并发是「几件活同时跑」,不是「按商家轮流」。商家 A 一口气提交 4 条长视频
  仍然能占满等待型的全部 gen 槽位,商家 B 的短活要等其中一条腾出来。#760 消掉的是「全平台
  只能做一件」,不是「按商家排队」。调度改造在 **#861**(已纳入 beta 门),本票不动调度。
- **按班告警**:`/api/health` 的顶层 `worker` 字段含义仍是「至少有一班在写心跳」;
  按班的真相在同一个 body 的 `workers` 里(每个角色一行)。据此告警属于 **#793**。

## 现场排查

- 「我的任务没人干」——先看目标服务启动日志的 `role=… — consuming …` 那行:队列不在里面,
  就是角色配错了,不是队列坏了。
- 「生成开始报 429 / 失败率上升」——先看 `provider REQUESTS` 那行乘上你的副本数,是不是超了 8。
- 「新部署上不去」——看 `/api/ready`;503 且 `reason: migrations-not-applied` 就是迁移没跑成,
  旧部署还在承载流量,先修迁移,别强推。
