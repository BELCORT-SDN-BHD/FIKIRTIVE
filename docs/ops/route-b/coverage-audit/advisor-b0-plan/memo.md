# B0 执行分解 · 首轮盲审意见

**结论先行：三个选项都不选原样，推荐第四方案 D——以 MATRIX-V0 为骨架、控制面亲手做全部判断列、舰队改派「逐源覆盖审计」而非「分源抽取」。** 理由核心：V0（143 行、含 promise_source）就是昨天已完成的抽取产物，方案 A 等于重做一遍并自造五份粒度不一的输出；方案 B 单脑穷举与 B0 的存在理由（防漏）正面冲突；方案 C 要么装不下上下文、要么把归块/定级判断塞给 worker，违反「判断永不下放」。审计与抽取的区别是承重的：审计 worker 对着**已冻结粒度**的草稿逐条走源文件，只能输出「命中行ID / MISSING / 建议出程」，发明不了颗粒——A 的主弊端就此消解，founder「施工派舰队」的口令也照办了。

## 1. 主结构：方案 D 的六步

1. **骨架**：脚本（优先，可复现零幻觉）或单个廉价 worker 把 V0 的 143 行机械转成 B0 九列 schema。**沿用 V0 的 id 作为功能ID（或建 1:1 对照列）**，保住通往 570 行证据分片的追溯链。新列以显式占位枚举 `TBD-Bn` 填充，不留空白。
2. **判断**：控制面亲自填所属块、六级初值、宪章处置，按 zone 分批做，不外包。
3. **审计舰队**：4–5 只只读 Sonnet lane，每源一只（蓝图第六章+宪法11条+九缝 / MASTERPLAN 全章 / A′ 舱单+65页注册表 / 缺失大陆前五+判决）。每条源项输出结构化三元组：源项引文与行号 → 命中矩阵行ID｜MISSING｜建议 charter-out（含「被判决取代 superseded-by-7-x」类别）。产出带计数的覆盖报告（形如「蓝图第六章：74 条承诺，71 命中，3 缺失」）。注册表由控制面先 `git show 54c1de0b:…/_registry.ts` 物化进证据目录并钉死 SHA，粒度按页/能力、不按 272 文件。审计只提议，处置权在控制面。
4. **裁决**：每条 MISSING 由控制面逐条裁决——加行（新ID）或入宪章「不在本程」（写明理由），全部进决策日志。
5. **机器校验**：repo 内脚本（可 codex exec 写）校验：ID 唯一、9 列非空（占位枚举合法、空白违规）、状态与块 ∈ 闭集、每源报告内每条源项有处置。**校验必须双向**——只查矩阵内部列永远查不出「源里有、矩阵没有」，而漏正是 B0 的头号敌人。
6. 顾问复审（矩阵+覆盖报告+宪章增补）→ **单一 PR** 交 founder 签。冻结必须是一个原子签署对象，分批合并会让「范围已冻结、可写产品代码」的触发点变模糊。

## 2. 五个子决策

1. **落位：`docs/ops/route-b/` 五文件。** 逐字核法：硬约束与 §五只说「五本账全在 repo」，未指定路径；§十一的本义是「`.orchestration/` 里的过程账必须入库走 PR」（M5 的病根是没提交），不是「账本必须住进点目录」。darwin Finder 默认隐藏点目录，而矩阵是后面 12 块每块验收都要引用的对象，藏起来对 founder 文件系统式管理不友好，也偏离 docs/ops/ 既有惯例。若编排运行时确实产生 `.orchestration/` 状态（如 epoch 认领），按 §十一 照常入库并放一个指针 README 指向 docs/ops/route-b/，两者不混。PR 说明里用一句话向 founder 挑明这个读法，消歧即终局。
2. **形态：按块一文件的 markdown 表**（`matrix/B01-….md` … + `charter-out.md`）+ 校验脚本 + 脚本生成的计数索引。矩阵不是写完就死的文件：六级状态是活列，后面每块的 PR 都要改自己那些行——单一大文件是 12+ 块并行下的冲突磁铁；CSV 牺牲 founder 可读性（你已自证）。markdown 表照样机器可校验（解析管道符即可），人读走块文件与生成索引，机器读走脚本，索引是生成物故无双源漂移。
3. **level-0：要，且显式。** 建议命名 `listed`。三个理由：「9 列齐全」的校验需要「空白=违规」才有牙齿；把无 spec 条目硬标 spec-ready 是「建毕」病的镜像；founder 看板需要诚实的「X/150 尚未起工 spec」。注意不改动、不重编 founder 已签的六级——在其下加第 0 级，作为决策日志条目并在 PR 说明中显式标出，让签字覆盖它。
4. **84 债：不加 84 行。** 对等债的本体是「能力行上 Otto skill 列的缺口」，另加行会让能力被双计。表达为三件套：债标注在其能力行（Otto 列取闭集值如 `missing(debt-nn)`）；每块由矩阵**生成**「本块 parity 清零清单」，块验收=清单为空（满足硬约束 3「随块清零」）；另立 `parity-debt.md` 对照表逐条列 84 号→行ID。校验点：84 条每条必须有处置（映射到行/成为块验收准则/出程），计数不许丢；映射不到能力行的基建类债，显式化为新行或块级准则，不许略过。
5. **存量 integrated：一律不进六级。** 六级是路线乙的**认证阶梯**，不是代码存在性描述——存量代码没有本程 spec、没过本程验收，标 code-complete 等于把未验证断言灌进认证列，正是被废除的「建毕」。但全压 0 级又丢掉「main 上确实能跑」的信息，对 founder 同样不诚实。解法是**双列诚实**：六级列从 `listed` 起（仅当蓝图/判决里确有可引用的已批 spec 时才给 spec-ready，批准来源列须给出处）；V0 的 `stage_main` 观察保留为独立「存量现状」列。看板于是读作「已认证 0 / 存量 integrated N」——这个差值本身就是路线乙的定义；存量的意义是让 B1–B13 升级快，不是预支认证。

## 3. 隐藏风险（B0 冻错的污染路径）

- **粒度错误是最大污染源**：行太粗，块可以在子能力缺失时宣告 release-certified（「建毕」在行内复活）；太细，状态维护崩坏。粒度规则要成文进矩阵 README（一行=一条对 founder 的能力承诺，拥有自己的人工入口或 Otto skill 或闸），审计按此匹配。
- **静默失范围**：源项既不入块也不入「不在本程」即凭空消失，数月后以「你答应过」的形式引爆。双向校验+每源计数是唯一解。反向也要防：charter-out 不许当难题回收站——每条出程须附 founder 可见的理由并计入合同计数。
- **ID 不稳**：冻结后增补若重编号，下游全部块报告/测试/PR 引用全断。规则：只增不改不复用；ID 不编码块号（块界可被修宪重划，ID 不能跟着断）；增补走决策日志。
- **归块错位**：能力放错块=在错误验收边界下被测，正主块「清零」时它不在场。PR 须明说 founder 签字冻结的四件事——行集、ID、归块、charter-out——之后只经修宪修改。
- **矩阵写完即死**：六级状态的价值全在「每块 PR 被迫更新自己行的状态并附证据」。B0 合同必须含**状态迁移规则表**（谁有权迁、每级要什么证据：sandbox-verified 要证据链接、live-verified 要 prod 溯源），否则 stage_prod=Unknown 会自我复制。这可能是 B0 除清单外最承重的交付物。
- **发布溯源断裂是全程地雷**：溯源不通则所有行的 live-verified 均不可判。B0 应把「发布溯源/部署可追溯」立为具名行或风险待裁条目并指定归属块，否则 12 个块各自撞墙各自即兴。
- **6 个💰/18 个 mock-变真点**：这些行的权限/花费闸列在 B0 就必须非 TBD（花费闸是程序级法律，不是块内设计）。校验点：18/18 有行有闸。
- **founder 复核过载→橡皮章冻结**：150 行×9 列逐行不可读。PR 主体应是一页 `B0-CONTRACT.md`（规则+计数+宪章增补+每源覆盖统计+相对 V0 的 delta），矩阵作附件——签的是合同，附的是附件；否则冻结权威日后必被翻案。
- **B0 自身范围蠕变**：别在 B0 给 B13 写测试计划。合同明文：B0 冻结清单+归属+状态语义+程序级闸；行内工程列在归属块 spec-ready 时硬化，占位必须是显式 `TBD-Bn`。
- **换届演练**：§五「第 1 块末尾故意换届演练」——无论「第 1 块」解析为 B0 还是 B1，建议就在 B0 末尾做：账本刚立、产品代码零行，是检验「办公室而非会话」的最便宜时点。

## 4. 补什么证据更稳

1. **30 分钟抽检定标**：拿宪法 11 条+缺失大陆五张工作清单（约 30 项）手工对 V0，测出预期漏率——漏率≈0 则审计 lane 减配，≈20% 则舰队设计是承重墙。这是决定 D 中审计轻重的最便宜实验。
2. 84 债原文粒度（每条是否指名能力），定子决策 4 的映射可行性。
3. V0 `stage_main` 词表枚举，定「存量现状」列闭集。
4. 判决 7-1~7-14 对蓝图条目的取代关系表，防止审计把「被判死」的东西误报 MISSING。
5. 编排运行时是否真会写 `.orchestration/`，定 §十一 执行细节。
6. founder 已签宪章的分区粒度与行粒度是否同阶；不同阶则 B0 需多交一张「来源→块」映射规则表。

## 5. 置信度

整体 **~80%**。分项：主结构 D 85%；账本落位 docs/ops/route-b/ 75%（§十一 存在被读成「账本必须住 .orchestration/」的空间，已给调和读法，PR 内一句话消歧）；按块分文件 80%；显式 level-0 90%；债不加行 80%（待 84 债原文佐证）；存量双列 85%。最不可让步的三条：双向覆盖校验、六级从零起证+存量另列、状态迁移规则随合同一起冻结——这三条任一缺失，B0 就会以不同方式把「建毕」病遗传给后面 12 块。
