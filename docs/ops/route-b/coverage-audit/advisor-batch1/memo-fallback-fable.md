## ① 批次结构:推荐 A′(四车道同启,B8 试产先行)

**L1 B10 代码车道**(两 worker、两 worktree)+ **L2 B9 spec** + **L3 B2 spec** + **L4 B8 设计试产 2 工位**。

- **不选 B 案**,因为它把依赖方向搞反了。B2 数据契约(事件/身份/同意)的最大需求方恰恰是 B8:CRM 起步的 Contact/ContactIdentity(`08-B8.md` B0-59~61)吃身份与同意契约,口碑量测(B0-63~67)喂 B2 的 B0-09。先冻 B2 再设计 B8,等于末期发现新 schema——正是 Sol 阻断的原情形。合同也是明文:§三 B8 行「设计全图**立即启动(不等债清)**」。正确拓扑是**并行 + 一个检查点**:B8 试产设计必须在 B2 spec 冻结前交出「数据契约需求单」,B2 吸收后才 spec-ready。
- **不选 C 案**。B10 三项是零判断量的工具修复,跑完它们证明不了 spec/设计机制的任何东西;且白白浪费 founder 当前的同日响应窗口(#239/#240 都当天合)和 ~3h 后回归的 SOL 复审能力。

## ② 六个子决策

**1. P0-2 与 P0-5:一个 worker、同一 worktree、顺序两个 PR(先 P0-2 后 P0-5)。** 两个 S 级 regex 改动开双 worktree 是纯协调开销且 ci.yml 必撞;合成一个 PR 则违反一 PR 一件事——它们是两条矩阵行(B0-81/B0-83)、两套红例自测证据。顺序化把 ci.yml 冲突消灭在源头。注意 P0-5 工作量已坍缩(见③),两个 PR 合计不过半天。P0-5 的修法直接抄 `verify-auth-guards.mjs:22` 已验证的双形状 regex 到 `check-parity.mjs:43`。

**2. P0-3:立即并行开工(第二个 worker、独立 worktree),不殿后。** 理由是窗口:现在是全仓唯一没有其它代码车道在飞的时刻(L2/L3/L4 全是文档),B10 后续行和 B3 施工一旦开始,全仓机械扫会变成冲突地狱。安全法采纳你列的第三项并细化:
- 第一步**重测**(128 是 2026-07-07 数据,此后 7+ 个 PR 落地),出「规则类别 × 数量 × 修法」清单;
- 控制面**按规则类别批修法**(不逐条);**行为可变类单列逐条过**(floating-promises 补 await 改时序、exhaustive-deps 补依赖改 effect 行为——这两类是「禁止顺手改逻辑」的真雷区);
- 三禁:禁 eslint-disable 铺洒、禁关规则凑零、禁触碰逻辑;
- ci.yml 倾向**独立 lint job**(check job 头注明示要保快,web-build 已有分 job 先例),worker 提案、控制面定;
- 与 L1a 的 ci.yml 冲突用合并次序解决:窗口内 L1a 两 PR 先合,P0-3 rebase 后合。

**3. B9/B2 spec 作者层级:控制面骨架 → Heavy worker 填证据 → 控制面终审 → 顾问 → SOL 跨族后冻结。** 判断不下放的边界画在**规范性 vs 描述性**:冻什么、契约形状、取舍、锚清单结构=控制面亲写;现状证据(file:line)、TS 签名、测试枚举、边界用例=worker(Opus/Sonnet-high,B0 审计舰队已验证可靠)。另一条:B9 冻的是**引擎契约**(registry 形状、manifest 三态语义 skill/exempt/todoSkill、上下文桥 E2-20 的接口、分域装载 E2-19 的域界),不是脚本实现行号——这样 L1 并行改扫描器不构成移动靶。

**4. B8 舰队:先 2 试产,模板冻结后 2-3 波铺开(每波 2-3 工位)。** 试产选 **CRM 起步**(最大化 stress B2 契约,身份/同意需求最重)+ **Campaign 一期**(2026-07-08 已有 spec 底,最快验证模板;且是上市点收入相关)。产出口径在你列的五件(六态+假设台账+对标锚+人工/Otto 双面+体量档位建议)之上加三件:
- **数据契约需求单**(新表/新事件/身份/同意诉求 → 喂 B2/B9 检查点);
- **逐行权限/花费闸初判**(💰行闸列非 TBD 是机器强制;B0-57 pack-confirm 是全舰单最高优先💰,试产期就要给出闸设计);
- **每大陆深度档位 A/B/C + 成本估算** = 体量过目的直接输入,让 founder 用 Q6 裁「做多深」时有可比数字。
产出全部是 docs PR,工单写死 read-only-to-code;对标锚是 spec-ready 硬门(无锚不开工),模板必须内嵌锚清单栏。

**5. spec 过目:「增量投递只读 + 合并窗口异议制」成立,带三个 carve-out 和一道手续。** 依据链:B0 合同 §一(founder 签署件)把 spec-ready 迁移权**明文给控制面**;总计划 §七 报告「增量投递、只读不需批」;§五 founder 窗口只做法定合并不做产品验收;加上 founder 本轮「直接开始就开始,我没有什么问题」。carve-out:(a) **B8 体量过目是合同明文的 blocking founder 裁决**,不适用异议制;(b) Q7 类(共享契约/钱/tenant/安全/品牌/申请材料/发布范围)永不攒批;(c) 修宪级 spec 内容立即停手上报——B0-79(D9)行内已写死「若需新豁免类别=修宪→停手报 founder」。手续:**先落一条 DECISION-LOG**(引 founder 原话+日期),并在下一份报告里一句话明示「spec 将只读增量投递、合并窗口前随时可异议、你的下一个 blocking 触点是 B8 体量过目」——把治理解释变成 informed default,founder 不认可随时可退,成本趋零。

**6. 状态迁移:随块 PR、PR 作者迁自己的行、控制面以 review 行使迁移权。** 矩阵按块分文件天然免冲突(L1 只碰 `10-B10.md`)。B0-81/83 这类工具行没有独立 spec 文件,建议:工单(含 MASTERPLAN P0 行验收+红例自测=锚)充当 spec,同一 PR 里 `listed→spec-ready→code-complete` 连迁两级(只增不跳=不越级,连迁不违反),TBD-B10 的测试/报告列同 PR 硬化。这是对合同 §一「spec PR 与代码 PR 分离」默认节奏的一处务实压缩,**落一条决策日志留痕**即可。

## ④ 隐藏风险(按杀伤力排序)

1. **五本账共享文件 × 四车道 = 攒批合并时连环冲突**(你点名的交互)。矩阵分块文件没事,但 DECISION-LOG / DEPENDENCY-STATUS / EVIDENCE-LEDGER / RISKS-PENDING 是单文件。解法:**worker PR 一律不写五本账**,账行以提案形式放 PR 描述;控制面在窗口收口时用一个 ledger-sync PR 统一入账。例外:必须先于开工存在的决策(如上面第 5 条的治理解释)单独小 PR 立即走。这个模式还预防了将来的四权分离问题——恢复 delegated merge 后「控制面实质编辑过的 diff 不得由控制面合并」,ledger-sync PR(控制面写、他人合)天然合规。
2. **攒批 × 栈式依赖。** P0-3 rebase 在 P0-2 的 ci.yml 上;窗口时控制面交「有序放行单」(合并顺序 + 每个 head SHA 的三关绿证据)。建议**向 founder 申请一个提前的首个 mini 窗口**,理由=首批全是围栏、零产品实质,早合让后续所有车道受 CI 保护;但计划不得依赖他持续同日响应。另注:2026-07-10 有「工程卫生 PR 可自合」授权在案,但本 session 已自设更严闸(任何 merge 当轮明示)——维持严闸+申请早窗,不要单方启用旧授权。
3. **P0-2 的「105 全是误报」是假设不是事实。** 加 `requireOwner` 后若仍有红,worker 必须分类:其它守卫形状(继续修 regex)vs 真无守卫(**安全发现,按 RISKS 准入规则不得攒批,Q7 立即上报**;修复属业务代码,超出「工具修复不碰业务」边界,另开 PR)。exit 0 之前不得接 CI。
4. **B9/B2 冻结时点。** 它们是本批最高后果产物;骨架与证据层现在就写,但 spec-ready(冻结)等 SOL 跨族复审跑完再迁——别为抢半天把引擎契约冻在单族评审上。
5. **控制面审查带宽是真正吞吐上限。** 四车道的判断审查+每块过顾问全汇到你这里,这是 B8 只开 2 试产的根本理由;第一周结束量一次自己的积压再决定铺开节奏。
6. **regex 的理论残余盲区。** 跨行类型注解的 `export const x: 长类型\n= async` 连加宽后的单行 regex 也认不出(verify-auth-guards 同病)。当前全仓为零,不值得追求完美 regex;在 P0-5 红例自测里加一个跨行用例,认不出就在工单里明示为已知边界留痕。
