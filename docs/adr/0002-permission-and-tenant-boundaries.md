# 2. 权限与租户边界

Date: 2026-08-03
Status: Accepted

## 背景

单一 `role` 字段无法表达一个人同时承担多个职责，也容易把“身份名称”误当成权限。
同时，仅靠调用处记得添加 `ownerId`，无法形成可靠的租户隔离基础。

## 决定

1. 平台权限存入 `UserRole`，组织权限存入 `MembershipRole`；一个人可同时拥有多个角色。
2. 角色只是能力组合。授权检查只问“是否具备此能力”，不会因为某个角色名称而禁止操作。
   例如同一成员可同时是 `creator` 与 `approver`，并取得两者能力的并集。
3. 旧的单一 `role` 字段只保留作兼容显示；它不授予权限。主角色由有效角色集合确定性推导。
4. 用户请求进入 `runAsUser` 后，Prisma 边界自动把租户模型的读写固定到该 `ownerId`。
   无租户的系统任务可扫描，但写入前必须进入 `runAsTenant`。
5. 两端都属于 tenant 的直接硬关系同时携带对象 ID 与 `ownerId`，由 PostgreSQL 复合外键拒绝跨租户连线。
   schema 回归测试会阻止新增裸 ID 关系；有意保留的软引用必须在 schema 注释中说明，并在实际写入路径验证归属。

## 后果

- 新能力通过角色能力表加入，不复制新的角色判断分支。
- 新的租户硬关系沿用复合外键模式。
- 真实行为由单元测试、集成测试和数据库约束验证；不再依赖庞大的源码模式扫描器宣称安全。
- 迁移若发现既有跨租户关系会直接失败，必须先调查数据，不会自动修正或吞掉异常。
