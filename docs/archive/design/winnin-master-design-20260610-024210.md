## Problem Statement

创始人（ComfyUI 重度用户，非程序员）目前用 ComfyUI（t2i / I2V / multi-reference / V2V / LoRA / I2I）+ LLM（构思、写 prompt）+ CapCut（拼接）+ 纸笔（分镜、脚本）制作 AI 视频。碎片化工具链之间**没有任何结构层**：

- references（角色、地点、产品、品牌素材）散落在文件夹里，靠手动管理
- 角色一致性靠手动"上一镜尾帧当 first frame"维持，无系统支撑
- 分镜与脚本在纸上，与生成环节完全断开
- 生成历史无法回链到 prompt、实体与参考图

当时的 Draft v1（现仅存于 Git 历史）把问题框定为"广告公司非技术用户用不来 AI 工具"，但本次诊断认为真实问题是：**已经会生成的重度创作者，缺一个把碎片串起来的结构层。**

## Demand Evidence

诚实记录，按证据强度排序：

1. **创始人本人是活的用户样本**（最强且唯一被验证的证据）：上述工作流是其每日真实流程，痛点为亲身经历，非想象。
2. **市场结构性信号**（间接）：创作者平均使用 AI 工具数从 1.2 涨到 3.4（碎片化加剧）；角色一致性被广泛公认为头号未解难题；ComfyUI 以 5 亿美元估值融资（2026-04），证明重度创作者要控制权而非简化。
3. **潜在投资人兴趣**：存在，但明确不计为需求证据（投资人兴趣 ≠ 用户需求）。
4. **外部用户验证：0。** 创始人无法说出一个具体的、可联系的目标用户。这是当前最大缺口，对应「The Assignment」。

未采集到的数据（创始人两次被问未答，列为待补）：
- 从想法到成片的单条视频总耗时
- 每月工具订阅 + 算力总花费

## Status Quo

```
想法 → 纸笔写脚本/分镜 → LLM 辅助构思和 prompt → ComfyUI 生成
（t2i/I2V/multi-reference/V2V/LoRA/I2I，一致性靠手动 first-frame 接力）
→ 文件夹里人肉管理 references 和产出 → CapCut 拼接 → 成片
```

断裂点：纸笔 ↔ 数字工具之间、生成 ↔ 历史之间、references ↔ prompt 之间，全部靠人脑和手工衔接。

## Target User & Narrowest Wedge

**第一用户：创始人自己**（前提 P1）。画像：能熟练操作 ComfyUI 复杂工作流的重度 AI 视频创作者；同时做客户商业视频、自有品牌内容与创作型短片。

**最窄楔子（前提 P2）：reference/实体管理 + @mention 语法。**

核心交互（创始人原话）：

> "如果可以在一个 chatbox 直接 like '@character is walking in @location holding @product'，处理完 reference 就最好"

实体（角色/地点/产品/品牌）成为**可寻址对象**，而不是文件夹里的散图。两个独立 AI（Claude 与 Codex 冷读）一致判定这句话是真正的产品核心。

**注意：** PRD 原定目标用户"广告公司创意制片人"降级为未验证假设（前提 P4），在 3 个以上真实外部用户验证前不作为开发依据。

## Strategic Positioning（2026-06-10 /plan-ceo-review 新增，D2 批准）

**一句话定位：模型中立的实体资产层——"references 的瑞士"。**

依据（2026-06 市场情报）：模型层正在内卷一致性——Kling 3.0 推出 character locking、Vidu 做 Multi-Entity Consistency、行业转向 Identity Anchoring/有状态架构。含义：

- **单模型内**的一致性会被模型层逐步解决，Fikirtive 不与之竞争（与 P3 自洽）
- Fikirtive 锚定模型层**永远不会做**的事：跨模型、跨镜头、跨版本的实体资产层——@Maya 在 Kling、Vidu、创始人的 Modal 端点之间通用；生成历史回链不依赖任何单一供应商
- 模型厂商竞争越激烈、方言越多，中立实体层越值钱；per-model adapter 架构（阶段二）即此定位的工程兑现
- 搜索未发现任何竞品在做 @mention 实体语法——核心交互目前是空白
- 风险对冲：若某模型厂商向上吞实体层（如 Kling 扩展 character locking 为完整实体库），Fikirtive 的防线是多模型中立性 + 用户已沉淀的实体资产库的迁移成本

此定位供后续融资叙事、竞品问答、官网文案复用。

## Constraints

- 创始人不写代码，开发将以 AI 协作（Claude Code 等）为主——架构必须偏向成熟、文档丰富的技术栈
- 结构层不做模型（前提 P3）：生成全部经外部模型 API 和/或本地 ComfyUI API
- 上游模型能力（一致性上限、API 稳定性）是产品体验的硬天花板
- 单人项目，无团队；阶段一无需多租户、计费、审批流

## Premises

经创始人逐条确认（D10），P1 经 Codex 挑战后创始人坚持原版（D12）：

1. **P1（创始人坚持原版）：** 第一用户是创始人自己；**V1 成功 = 完全取代其现有 ComfyUI+LLM+CapCut+纸笔拼装流程。**（Codex 建议改为"每天用作控制层即算成功"，创始人否决；张力通过分阶段路线消解——见 Recommended Approach。）
2. **P2：** 切入楔子是 reference/实体管理（@mention 语法 + 一致性辅助），不是一次做全的平台；其余环节围绕楔子生长。
3. **P3：** Fikirtive 做结构层/编排层，不做模型；生成调外部 API / ComfyUI。
4. **P4：** PRD 的广告公司切入点与定价章节降为未验证假设。

附加设计要求（创始人提出）：**agentic 如何实现**——已在 Recommended Approach 的 Agentic V1 小节回答。

## Cross-Model Perspective

Codex（gpt-5.5，read-only 冷读，2026-06-10）独立结论：

- **最强版本：** "Fikirtive 不是 AI 视频生成器。它是面向重度 AI 视频创作者的**连续性与 reference 控制层**……让 @character、@location、@product、品牌素材在 prompt、镜头、版本、工具之间可复用。"
- **最有揭示性的回答：** 即创始人 @mention 原话——"这就是真正的产品。实体变成可寻址对象，而不是散落在文件夹和记忆里的图片。"
- **挑战的前提：** P1 的"完全取代"成功标准。Codex 认为更好的标准是"他是否每天把 Fikirtive 当 reference/分镜/控制层用，底下继续用 ComfyUI/CapCut"。**创始人知情后仍坚持原版 P1。**
- **48 小时原型建议：** 本地 web 应用（Next.js + TypeScript + SQLite + 本地文件存储），实体库 + @mention 编辑器 + 镜头板 + 生成历史 + ComfyUI 导出/API；跳过时间线、campaign、persona、审批流、定价、LoRA 训练、自主生成。
- **Agentic V1：** "agent 不应自主做视频，应是围绕实体图谱的结构化助手……每次生成前请求人工批准。架构 = 实体库 + 镜头库 + 确定性工具 + LLM 规划/检查器 + 人工审批。"

跨模型一致度：两个独立模型在"楔子 = reference 控制层"“@mention 是核心交互”“agentic 要小而受控"三点上完全一致；唯一分歧（V1 成功标准）已由创始人裁决。

## Approaches Considered

### Approach A: Reference 控制层（最小可行）
- Summary: 本地优先 web 工作台：实体库 + @mention prompt 编辑器 + 镜头板 + 生成历史 + ComfyUI 导出/API。
- Effort: S-M（CC 协作约 2-4 周）　Risk: Low
- Pros: 最快验证；技术风险最低；两个 AI 共同背书的起点；若创始人自己都不每天用，可最早止损
- Cons: 按原版 P1 只是里程碑而非终点；不取代任何现有工具
- Reuses: ComfyUI API、模型 API、Next.js+SQLite 成熟栈

### Approach B: 分阶段全替代工作室（理想架构，含 A 为第一阶段）
- Summary: 三阶段：①Reference 楔子（= A 全部内容）→ ②生成编排进站内（模型路由、任务队列、结果回流、版本对比）→ ③轻剪辑/拼接（镜头排序、转场、配乐、导出）。架构自第一天采用 PRD §11 收缩版骨架：一个 Copilot + 确定性工具 + 工作流引擎 + 人工审批门。
- Effort: XL（CC 协作约 3-5 个月）　Risk: Med-High
- Pros: 唯一完整满足原版 P1；每阶段有可用产出；架构为终局设计
- Cons: 总周期最长；阶段③"轻剪辑"边界易膨胀，正面接触 CapCut 主场
- Reuses: A 的全部代码与数据模型；PRD §11/§12 架构思路（收缩版）

### Approach C: Chat 即工作台（创意/横向）
- Summary: @mention chatbox 即主界面，实体库/镜头板/历史是对话旁自动物化的侧栏；Copilot 全程编排，审批内嵌对话流。
- Effort: M-L（CC 协作约 4-8 周）　Risk: Med
- Pros: 差异化与 demo 传播力最强；范式成立则护城河深
- Cons: 重度生产场景纯聊天可能低效；范式失败则 UI 层重来
- Reuses: A 的实体/镜头数据模型

## Recommended Approach

**Approach B：分阶段全替代工作室**（创始人于 D13 选定）。

理由：唯一同时满足创始人坚持的 P1（全替代终点）与 P2（楔子切入）的路线；第一阶段即 Approach A，数周内即有每日可用的真产品，同时每行代码都通向全替代终点。

### ⚠ 形态修正（2026-06-10 /plan-eng-review D3-D5，创始人澄清）

**Fikirtive 是云端 SaaS（浏览器访问的网页平台），不是桌面应用、不是本地优先工具。** 此前文档中"本地优先"的表述源自 Codex 冷读的 48h 原型建议，与创始人在 D5 已表达的平台意图（"接第三方 API 让用户在我们的平台使用"）存在未对齐的矛盾，本次评审修正。落地三决定：

1. **云端起步（D3）：** 第一天即部署上云，创始人通过网址访问；与 Modal 生成同在云侧，素材回流零绕路；验证成功后零搬家。
2. **阶段一收录通道 = 浏览器拖拽/批量上传（D4）：** 云端无本地文件夹可监视，原 watch-folder 方案作废；Modal/API 自动回流随阶段二编排上线；可选的本地迷你同步器记入 TODOS 待验证后评估。
3. **登录（D5，经 D18 修订升级）：** Auth.js 邮箱魔法链接（无可泄露的共享密码；会话过期/安全 cookie/登录审计随框架自带；即未来多用户 auth 的地基，零重复工程）；正式多用户功能仍延至 P4 验证门后。

技术栈随之回归：**Next.js（App Router）+ TypeScript + Prisma 7 + Postgres（第一天即 Postgres，SQLite→Postgres 迁移问题整体消解）+ 云对象存储（内容哈希为 key）**。桌面壳问题（Electron/Tauri）整体消解。不变的部分：楔子、M0 四件套、双门、阶段门、LoRA 例外、Qwen 时机、Tiptap 编辑器、ComfyUI 模板包格式、实体包格式与安全约束。

### 阶段定义与升级门（gate）

- **阶段一「Reference 控制层」**：实体库（角色/地点/产品/品牌；名称、别名、参考图组、笔记、负面约束、偏好 prompt 词）；@mention prompt 编辑器（@呼出实体，芯片化展示）；镜头板（镜号、描述、所用实体、prompt、产出、状态）；生成历史（产出回链 prompt+实体+参考图，版本堆叠）；ComfyUI prompt 包导出。**云端 SaaS 单实例、单用户（创始人）、Auth.js 魔法链接登录、无计费**（D3/D5/D18）。
  - **里程碑 M0「最小可用核」（2026-06-10 CEO 评审 D19 批准，外部声音 #18 采纳）：** 实体库 + 镜头板 + 手动挂产出 + @编辑器四件套**最先落地**（目标第 1-2 周可用）；升级门计数从 M0 可用日起；其余批准项（实体包、微交互、状态面板等）在升级门窗口内陆续落地。施工顺序铁律：任何扩张项不得阻塞 M0。
  - **Gate 0「观察前置门」（D20 批准，外部声音 #4/#20 采纳）：** 开发可以开始，但**商业化叙事冻结**（瑞士定位对外使用、生态功能、外部用户功能均不启动），直到创始人完成 ≥3 个重度创作者的真实 reference 工作流观察（The Assignment 第 2 项）。观察结果直接校准 P4 验证门。
  - **停止门（D20 批准，2026-06-10 eng-review D23 随升级门重设同步修订）：** 完成首个真实项目后，**下一个真实视频项目创始人没有自然地回来用 Fikirtive**（系统记录的实质动作为证），则冻结一切扩张、回到诊断重审——不得带着失败信号硬推阶段二。
  - **产出收录路径（D4 形态修正）：** 阶段一唯一通道 = **浏览器拖拽/批量上传**（直传对象存储 + 断点续传，多 GB 视频可靠完成），新上传入候选区由用户挂到镜头。**候选区位置：底部"生成历史"面板的「未挂载」过滤视图**（线框图需补此 delta）。Modal/第三方 API 生成结果的自动回流随阶段二编排上线；可选本地迷你同步器在 TODOS。
  - **镜头状态机（最小集）：** `草稿 → 已导出 → 已挂产出 → 定稿` 四态；状态流转细则与是否需要"生成中"态由 /plan-eng-review 定稿（阶段一无站内任务派发，"生成中"大概率不需要）。
  - **扩张追加（2026-06-10 /plan-ceo-review，EXPANSION 模式逐条批准）：**
    - **E1 实体资产包：** 实体可导出/导入（JSON 清单 + 素材 zip，含参考图组、prompt 词、负面约束、LoRA 指针、版本号）。兼作备份/迁移；为远期实体包生态保留期权。
    - **E2 万源收录总线（D4 形态修正后）：** 任何工具的产出都能进 Fikirtive——阶段一通过浏览器拖拽/批量上传（不限来源），阶段二加 Modal/第三方 API 自动回流；可选本地迷你同步器（监视本地夹自动上传）在 TODOS 待验证后评估。"不限生成工具的总账本"叙事不变，实现通道由 watch-folder 改为上传+回流。
    - **E6 喜悦包（5 个微交互）：** ①拖图到任意位置自动建实体 ②@ 自动补全显示参考图缩略图 ③镜头卡"尾帧→下一镜首帧"一键按钮（阶段一行为：从已挂载视频产出提取尾帧，存为下一镜 first-frame 参考图槽位，随导出包带出）④镜头卡悬停滑览全部版本 ⑤联络表（contact sheet）一键导出。
    - **E4 前置：** 生成历史 schema 预留"可模板化"结构——prompt 模式/模型/参数/实体引用分字段存储，而非整段文本（配方功能阶段二上）。
    - **E1 导入语义：** 导入冲突/合并与 LoRA 指针跨机失效处理由 /plan-eng-review 定稿。
    - **数据安全（D10 原则不变，实现随形态修正）：** "单点故障 ≠ 资产归零"仍是阶段一底线，云端形态下实现为：托管 Postgres 自动备份 + PITR（时点恢复）必须开启并验证过一次恢复演练；对象存储开版本化/软删除保护；E1 实体包导出兼作用户侧逃生通道（数据可携带，不被平台锁死）。
  - **@mention 展开规则（阶段一只做 ComfyUI 方言）：** @实体芯片在导出时做两件事——别名/偏好 prompt 词的文本替换 + 该实体参考图组打包进对应模板槽位。多模型 prompt 方言延期到阶段二的 per-model adapter。
  - **删除/改名语义（简化版定案）：** 全表软删除（`deleted_at`）；生成历史存**不可变快照**（生成当时的实体名 + 参考图内容哈希），实体改名/删除不破坏任何历史记录。细化由 /plan-eng-review 负责。
  - **升级门（2026-06-10 eng-review D23 重设，创始人按自身 24/7 生产节奏选定纯项目计数版）：** **连续 3 个真实视频项目**的 references/分镜/生成历史全程在 Fikirtive 管理（由系统自动记录的实质动作判定：建/改实体或镜头、挂载产出、导出模板包），才开建阶段二。无日历时间底线——产得快门就过得快；新鲜感假阳性风险已知情接受，停止门为兜底。
- **阶段二「生成编排」**：站内模型路由、任务队列、结果自动回流镜头板、版本对比视图。
  - **不做"统一抽象"。** 前置步骤：先做目标模型能力矩阵（multi-image reference / first-frame-only / 专有 character-ref API 等注入方式互不兼容），再写**带能力标签的 per-model adapter**——按各模型真实能力暴露，不向最小公分母看齐。
  - **ComfyUI 集成方式：** 不做通用连接器。从创始人自己的真实工作流图导出 **N 个精选、带版本号的参数化模板**（覆盖 t2i/I2V/V2V/multi-ref/I2I 等其常用模式），Fikirtive 按模板版本映射参数槽位；创始人改图后重新导出并升版本号，旧任务记录保留旧版本引用。
  - **扩张追加（2026-06-10 /plan-ceo-review）：**
    - **第三方模型 API 明确纳入 adapter 范围：** Seedance、Gemini/Veo 等外部模型 API 与 Modal 端点同走 per-model adapter + 能力矩阵（创始人 D5 确认 "all in one" 方向）。「用户自带 key vs 平台代付」延期至商业化验证门后（TODOS）。
    - **E4 配方记忆：** 成功生成一键存为配方（prompt 模式 + 模型 + 参数，实体位留槽），从配方启动新生成。
    - **E5 成本预告牌：** 模型注册表每端点带 cost_rules；派发前显示预估费用与耗时（只显示不扣费，credits 体系仍延期）。
  - **升级门：连续 4 周创始人的全部生成任务经 Fikirtive 派发，才开建阶段三。**

### 创始人补充的技术决策（D15 随批准提供）

- **ComfyUI 工作流以 API 形式打包，部署在 Modal（serverless GPU）上**，由创始人自行完成打包；Fikirtive 把这些端点**当作模型来调用**。影响：①阶段二的"精选版本化模板"方案升级为"Modal 端点注册表"——每个端点等同一个带能力标签的模型条目，与外部模型 API 走同一 per-model adapter 机制；②（D4 形态修正）阶段一收录靠浏览器上传，Modal 结果自动回流随阶段二编排上线——SaaS 与 Modal 同在云侧，回流为存储到存储的零绕路传输。

### Agentic V1 实现（回答创始人 D10 的附加问题）

采用「小而受控」模式（两个 AI 一致推荐，亦与 PRD §11 guided-autonomy 哲学同源）：

```
实体库(DB) + 镜头库(DB) + 确定性工具 + LLM 规划/检查器 + 人工审批门
```

V1 的 Copilot 职责清单（白名单制，仅此五项），**按阶段分配**：
1. 把 brief/想法解析为实体与镜头提案（草稿态，人批准后落库）——**阶段二**（需 LLM 规划器）
2. 检测缺失参考图——**阶段一**（纯规则，不需 LLM）：规则为**计数制**——镜头引用的实体参考图数为 0 或低于阈值时告警；"缺侧视图"这类**视角级**判断需要逐图元数据或视觉推断，归**阶段二**（届时为参考图组加可选视角标签）
3. 把 @mention 展开为模型专用 prompt——**阶段一只做 ComfyUI 方言**（确定性模板替换）；LLM 润色与多模型方言为**阶段二**
4. 跨镜头连续性检查（服装、地点、道具、品牌规则）——**阶段二**（需 LLM/视觉检查器）
5. 建议 prompt 变体与 first-frame 接力策略——**阶段二**

线框图中的"Copilot 检查区"在阶段一仅显示规则类检查（职责 2、3）；LLM 建议类条目（职责 1、4、5）为阶段二占位。

**铁律：任何生成调用前必须人工批准。不做"一句话 → 成片"的自主 agent。** agent loop 与固定 workflow 的取舍（PRD 问题清单 C1）在 V1 答案为：固定 workflow + 白名单工具，无自由 agent loop。

**空状态即引导（2026-06-10 CEO 评审 D17 批准，规格约束）：**

每个空状态（空实体库/空镜头板/空候选区/空历史）必须是**可操作的引导**——直接教用户下一步（如空实体库显示"把一张角色图拖进来试试" + 虚线拖放区）。纯"暂无数据"占位不允许出现。首次启动体验 = 14 天门的第 1 天。全部交互状态格子（loading/empty/error/partial）的具体设计由 /plan-design-review 逐一补全。

**性能护栏（2026-06-10 CEO 评审 D15 批准，规格约束）：**

1. **缩略图/尾帧提取后台队列化：** CPU 重活全部进 worker 的 pg-boss 队列（D9/D10），界面先显示占位图渐进填充；任何上传量都不得冻结 UI；多 GB 视频提帧用预签名 URL 范围读，禁止全量下载。
2. **长列表虚拟化：** 生成历史、候选区等无界增长列表从第一版就虚拟化（只渲染可见区），"越用越卡"不允许发生。

**可观测性（2026-06-10 CEO 评审 D16 批准）：**

1. **服务端结构化日志（形态修正后）：** 上传/收录/任务执行/导出/回调事件每条留痕（时间戳 + 上下文），落 Railway 日志与 pg-boss 任务记录；任何"东西去哪了"的问题可从日志+任务历史重建现场。
2. **系统状态面板（形态修正后）：** 聚合显示上传会话状态、worker 心跳、队列深度与失败任务数（pg-boss dashboard 数据）、R2 可用性、备份/PITR 状态——附录 A 各失败信号的聚合层；面板视觉设计交 /plan-design-review。

**安全约束（2026-06-10 CEO 评审 D13 批准，架构级，实现细节归 /plan-eng-review）：**

1. **实体包导入按不可信输入处理：** 解压时校验路径（防 zip-slip 路径穿越）、限制包大小与文件数（防解压炸弹）、版本校验拒绝过新格式。该约束从实体包格式定型（阶段一）第一天生效——格式的设计意图就是未来跨创作者分享。
2. **密钥永不入库、永不入包（形态修正后）：** 模型 API 密钥（Modal/Seedance/Gemini/R2 等）只存托管平台 secret 管理（Railway 环境变量），永不写入 Postgres；实体包导出、备份、配方分享因此物理上不可能携带密钥。阶段二明确：**仅创始人的服务端密钥，无任何外部用户可触达的 key 通道**（BYOK vs 平台代付延期至 P4 后，见 TODOS）。
3. **R2 直传加固（2026-06-10 eng-review D19 批准，外部声音 #2/#4/#10 采纳）：** ①预签名签发时限定 key 前缀/大小上限/MIME/过期/分片数；②对象 key 含 owner 命名空间（`u/<owner_id>/<hash>`），防未来跨用户哈希探测；③客户端哈希仅作秒传预判，**worker 服务端复核哈希通过后才入库关联**（客户端不可信铁律）。
4. **云端删除语义（D21 批准，外部声音 #12 采纳）：** 软删后 30 天保留窗（可反悔恢复）；到期后 pg-boss 定时清扫任务按**引用计数**判定——同一哈希被多处引用（去重共享），引用归零才真删 R2 对象及衍生物（缩略图/尾帧）；生成历史的不可变快照（纯元数据）永不物理删。

## 标准开发流程（2026-06-11 创始人提议，已采纳）

每个**新垂直切片**（剪辑条、R2 直传、阶段二生成引擎…）按三件套推进：

1. **Contract-first**：合同住在 `packages/core`（zod schema + TS 类型），web/worker 同源 import——typecheck 即验约。外部面（Modal 回调、第三方 API）合同带版本号 + HMAC。
2. **Frontend-first**：UI 对着合同生成的 mock 开发（创始人用眼睛决策；UI 返工是分钟，管线返工是天）。
3. **Tracer bullet**：最细的端到端穿透弹先打通全部关节（UI→action→队列→worker→存储→回显），再填肉。

**四条铁律**：① mock 绑定 tracer，tracer 通日即 mock 死期（防 LTX 式 teaser chrome）；② 合同只住代码不住文档；③ tracer 是正式骨架不是草稿，打完不扔；④ 只适用新切片，不回头给已真实接通的 M0 套 mock。

顺序裁决：T3 鉴权先行（tracer 落线上前必须有墙）。

**鉴权门触发条件（2026-06-11 创始人裁决）**：T3 已建成但线上默认关（AUTH_ENABLED 开关）。**硬触发**：任何会产生费用的端点上线前（剪辑渲染 tracer、API key 生成），必须先设 AUTH_ENABLED=true + RESEND_API_KEY。此条与开发流程的"tracer 落线上前必须有墙"互为印证。
