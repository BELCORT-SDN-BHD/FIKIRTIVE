# 零排队（视频不占位）规格书

> 批准: Founder 2026-09-13 对谈裁决——先裁方向「根治方案本版就要，不等新票」，再批本规格全文「批准，含探针预算（≤US$2）」；出身链见 §6。
> 规格前缀: QUEUE（验收编号 = QUEUE-A1、A2…，全仓不与其他规格撞前缀）

## 0. 一句话

长视频在供应商那边生成的十几分钟里，不再占用我们机器的施工位——别的商家的活立即开跑，商家感知零排队。

## 1. 九问

1. **商家做什么动作、看到什么结果？** 商家 A 连发 4 条长视频后，商家 B 提交短任务，B 的任务立即开始生成，不用等 A 的任何一条拍完。今天 B 最坏等约 16 分钟。
2. **入口在哪里？** 无新入口。所有现有生成入口（Otto 确认卡、画布、排期）行为不变，只有等待时间变短。
3. **四态？** 无新 UI。卡片状态照旧（排队中／生成中／完成／失败）。
4. **数据从哪来、写到哪去？** 供应商任务单号已存在 GenJob（`generationIds`，崩溃续拍机制现成）。改动＝视频提交成功后不再原地轮询到完，而是结束本次认领、用带延迟的重排消息回来查进度；查到终态才走现有交付路。需要的新字段（如提交时刻、下次查询时刻）在施工稿定，全部落 GenJob payload，不建新表。
5. **碰不碰钱路？** 碰（gen 是 reserve→settle 钱路）。**幂等键与账目语义逐字不变**：提交前 reserve、成功恰一次 settle、失败恰一次 refund，键仍是现有 CAS 与结算键。改的是等待的姿势，不是账。
6. **权限与租户边界？** 不变。worker 系统帧照旧（`runAsSystem("worker-job-dispatch")` 等封闭词表）。
7. **参考对照？** Mux、AWS MediaConvert 的异步任务模式：提交拿单号、放手，靠回执或轮询收结果，工人不守着等。供应商本身就是这个语义：任务有服务端 `queued` 状态、FIFO 队列、支持 `callback_url`（docs.byteplus.com/en/docs/ModelArk/1520757，2026-09-13 调研，证据待随探针入 docs/audits/）。超并发提交会被接进服务端队列而非拒绝；排队数超上限才 429（`QuotaExceeded`，该 code 复用 3 义，必须按 message 区分）。
8. **胃口？** 重挡（钱路计时结构改造）。一轮施工＋判官；探针预算 ≤US$2。超出即砍范围回呈。
9. **Otto 怎么协助？** 不适用（底层调度改造，Otto 面自动受益）。

## 3. 不做（非目标）

- **不做 `callback_url` 回执**：需要公网回调端点＋验签，延迟轮询已够。触发条件＝轮询 RPM 实测撞限或任务量规模化后另立票。
- **不抬供应商并发闸门**（保持 6）：账户安全余量保留，Founder 2026-09-13 裁定不走抬并发路线。
- **不做长短活分池**：根治后视频不占位，无需分池（同日裁定）。
- **图片路不改**：图片是同步 HTTP（5 分钟内完成），占位合理。
- **不动施工位数量**（gen 4 照旧）：放手后施工位周转以秒计，数量不再是瓶颈；要抬另议。
- **不动 #1430 已合入的撞限速让位兜底**：保留为极端场景的第二道保险。

## 4. 异议栏（AI 必填）

- 最大风险＝时钟语义换锚点时漏改一处旧锚点：在飞视频不再持有施工位后，35m 卡死判定若仍按「认领后经过时长」判，会把健康视频误判失败并退款、供应商照收钱——正是本票要消灭的病反向复发。防线＝clock-invariants 全套先行红绿＋QUEUE-A6 逐条改写，判官红案复现。
